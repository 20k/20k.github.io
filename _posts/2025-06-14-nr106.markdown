Hi there! Today we're going to examine how to do N-body particle physics, in general relativity. This is a bit of an underexplored topic compared to Newtonian N-body, and its easy to accidentally pick the wrong formalism or techniques for solving this problem. While the basic theory of what we're doing isn't complicated, there's a few major numerical problems to tackle today

At the end of this topic, we'll have about 10 million particles up and running at a decent speed - you'll also have received a crash course in IEEE floats, and the problems a spec defect in C++ can cause

# What are we doing?

In both General Relativity, and Newtonian physics, we deal with pointlike particles when doing N-body dynamics. Each particle is fully described by its mass, position, and velocity in both formalisms

In Newtonian physics, each particle directly exerts a force on all other particles, which is famously:

$$F = \frac{G m_1 m_2}{r^2}$$

In general relativity, particles act through the (4d) stress energy tensor, and do not *directly* interact. For a single particle [(2.5)](https://scispace.com/pdf/3d-numerical-simulation-of-black-hole-formation-using-43u5c2u959.pdf0):

$$
T_{\mu\nu} = m \alpha^{-1} W^3 \delta^{(3)}(x^i - x_{\mathrm{p}}^i)\frac{u_\mu u_\nu}{u^0}\\
$$

|Symbol | Meaning |
|-|-|
|$m$ | The rest mass of a particle |
|$\alpha$ | Lapse, evaluated at $x^i$ |
| $W$ | Conformal factor, evaluated at $x^i$ |
| $\delta^{(3)}(x)$ | The 3d dirac delta function - this only takes a nonzero value when $x = 0$. This a non trivial term, and we'll have to discretise this |
| $x^i$ | The current coordinate position you're looking at |
| $x^i_{\mathrm{p}}$ | The position of the particle |
| $u_\mu$ | The 4-velocity of a particle, lowered |
| $u^0$ | The lorentz factor |

This is simply summed across all particles. Particles as you'd expect simply move via the geodesic equation, which is:

$$u^\mu \nabla_\mu u_\nu = 0$$

Clearly, we need to transplant this into the ADM formalism and spell out the equations more, but for once the general relativistic side of this is straightforward

# These equations in the ADM formalism

## Stress-energy

We need the ADM projections of the stress energy tensor $T_{\mu\nu}$, to calculate the compatible terms for the BSSN equations. These are [(2.14, 2.15, 2.20)](https://scispace.com/pdf/3d-numerical-simulation-of-black-hole-formation-using-43u5c2u959.pdf):

$$
\begin{alignat}{2}
\rho_H &= \alpha W^3 &&\sum m u^0 \delta^{(3)}(x^i - x^i_{\mathrm{p}})\\
S_i &= W^3 &&\sum m u_i \delta^{(3)}(x^i - x^i_{\mathrm{p}})\\
S_{ij} &= \alpha^{-1} W^3 &&\sum m \frac{u_i u_j}{u^0} \delta^{(3)}(x^i - x^i_{\mathrm{p}})\\
\end{alignat}
$$

These quantities will be evaluated at every cell in our grid - except for $u^0$, which hides a significant amount of interpolation at $x^i$ in its calculation

## The geodesic equation

Given a 4-velocity $u^\mu = \frac{dx^\mu}{d\tau}$, the spatial components $u_i$ are evolved as follows [(2.9)](https://scispace.com/pdf/3d-numerical-simulation-of-black-hole-formation-using-43u5c2u959.pdf):

$$\begin{align}
\frac{d u_i}{dt} &= - \alpha u^0 \partial_i \alpha + u_j \partial_i \beta^j - \frac{u_j u_k}{2 u^0} \partial_i \gamma^{jk}\\
u^0 &= \frac{\sqrt{1 + \gamma^{ij} u_i u_j}}{\alpha}\\
\end{align}
$$

The particle's position is evolved as follows (via $\frac{dx^i}{dt} = \frac{u^i}{u^0}$):

$$
\frac{dx^i}{dt} = -\beta^i + \frac{\gamma^{ij} u_j}{u^0}
$$

Note that all the quantities evaluated here need to be interpolated from the grid at the particle's position $x^i_\mathrm{p}$ - keep this in mind for $u^0$. I precalculate $u^0$ in the evolution step, and re-use that in the stress-energy calculation

# The dirac delta function $\delta(x)$

The  1d dirac delta function $\delta^{(1)}(x)$ has the following definition:

$$\delta^{(1)}(x) =
\begin{align}
\begin{cases}
0, \; &x \neq 0 \\
\infty, \; &x = 0
\end{cases}
\end{align}
$$

$$\int^\infty_{-\infty} \delta^{(1)}(x) \; dx = 1$$

This says that the dirac delta function only takes a value at a single point $x=0$, and the area under this point is precisely $1$. No real function actually meets this definition, so we must numerically approximate it somehow. Higher dimensional diracs are denoted by the raised index, eg $\delta^{(3)}(x, y, z) = \delta^{(1)}(x)\delta^{(1)}(y)\delta^{(1)}(z)$

## Numerical approximations

There are an extremely wide variety of approximations we can use - these basically smear out the function over a small area. We might demand that this new function has a few properties:

1. It is compactly supported, ie it has finite extent
2. It is smooth-ish
3. This function has an integral of 1

There isn't a super specific[^okso] reason to use one approximation over another. The dirac delta function I'll be pilfering today is [this one (20)](https://arxiv.org/pdf/1611.07906), which operates in 3d (though it is a function of radius)

[^okso]: One property it would be nice if our dirac could maintain is that the generated effective self force is exactly 0. I'm not sure if its possible to construct such a dirac though

$$
\Delta_1^{(3)}(r, r_s) = \frac{1}{\pi r_s^3}
\begin{align}
\begin{cases}
1 - \frac{3}{2} (\frac{r}{r_s})^2 + \frac{3}{4} (\frac{r}{r_s})^3 \;\; &\mathrm{for}\;\; 0 \leq \frac{r}{r_s} \leq 1\\
\frac{1}{4}(2 - \frac{r}{r_s})^3 \;\; &\mathrm{for}\;\; 1 \leq \frac{r}{r_s} \leq 2\\
0 & \mathrm{otherwise}
\end{cases}
\end{align}
$$

Where $r_s$ is the size in world coordinates of your particle, ie its a constant. Many papers make the simple substitution $\delta^{(3)}(x, y, z) \rightarrow \Delta^{(3)}(r)$, although this is a bit problematic

## Improving the numerical approximation

There's a bit of problem with making this simple substitution. To examine this, lets step back into 1D, and imagine a very basic dirac delta function $\Delta^{(1)}$:

$$\Delta^{(1)}(x) =
\begin{align}
\begin{cases}
1 - x, \; &\mid x\mid < 1 \\
0, \; \mathrm{otherwise}
\end{cases}
\end{align}
$$

When discretising, we create cells which are separated by a space of $h$. Our grid structure *samples* this function at eg $x-2h, x-h, x, x+h, x+2h$. If we evaluate the quantity:

$$\sum_1^n \Delta(x_n) \; h$$

We want that to be *precisely* $1$ - that is to say our area under the dirac delta function has been preserved. In our discretisation as it stands currently, there is absolutely no guarantee of it - this is only true in the limit as $h \rightarrow 0$. In fact, with small dirac delta function sizes (eg imagine its much smaller than a grid cell), this may be out by a significant amount!

The remedy is to calculate the exact amount of the dirac delta function that intersects with a grid cell. We can do this by integrating:

$$\Delta^{(1)}_{\mathrm{good}} = \frac{\int_{x - \frac{h}{2}}^{x + \frac{h}{2}} \Delta^{(1)}(y) dy}{h}$$

in one dimension, or in three dimensions:

$$\Delta^{(3)}_{\mathrm{good}} = \frac{\int_{z - \frac{h}{2}}^{z + \frac{h}{2}} \int_{y - \frac{h}{2}}^{y + \frac{h}{2}} \int_{x - \frac{h}{2}}^{x + \frac{h}{2}} \Delta^{(3)}(\textbf{V}) d\textbf{V}}{h^3}$$

Where $x, y, z$ are the coordinates of a grid cell in world coordinates

# IEEE and C++: A joyous combination

Let's examine the form of a general 1D problem, discretised onto a grid:

|Cell Index|0|1|2|3|4|5|6|
|-|-|-|-|-|-|-|-|
|Value|$a_0$|$b_0$|$c_0$|$d_0$|$c_0$|$b_0$|$a_0$|

I've set up the initial conditions such that they're symmetric about the index $3$. After a single timestep into the future, we might expect our initial conditions to evolve to a new state:

|Cell Index|0|1|2|3|4|5|6|
|-|-|-|-|-|-|-|-|
|Value|$a_1$|$b_1$|$c_1$|$d_1$|$c_1$|$b_1$|$a_1$|

For any correct simulation, that symmetry should be preserved. In virtually all simulations however, you'll very immediately notice that this property does not hold up - and the two sides of the grid start to *increasingly* diverge. This is despite having the same initial conditions on both sides!

## Root causing the problems

This can be root caused to two similar problems:

1. Floating point arithmetic is not associative
2. How C++ handles floating point expressions, via a little known loophole in the standard

Asymmetry can sneak in anywhere we look at adjacent grid cells or non central values (eg the dirac integral bounds). A first culprit to look at is differentiation. In general, 4th order numerical derivatives get implemented as follows:

```c++
float diff(const std::vector<float>& points, int idx, float scale)
{
    return (points[idx - 2] - 8 * points[idx - 1] + 8 * points[idx + 1] - points[idx + 2]) / (12 * scale);
}
```

This is evaluated from left to right. Lets check what we get for indices $2$, and $4$ - which should return exactly the same result:

$$\begin{align}
\mathrm{diff}_2 &= ((a_0 - (8 b_0)) + (8 d_1)) - c_1\\
\mathrm{diff}_4 &= ((c_0 - (8 d_0)) + (8 b_1)) - a_1\\
\end{align}$$

The issue is that after each floating point operation, a *rounding* step is performed implicitly. This means that these two expressions don't return the same results! This isn't a theoretical problem either, here's an example in [real-world code](https://github.com/GRTLCollaboration/GRChombo/blob/130140afe972701575740685343ea28f6ab8234c/Source/BoxUtils/FourthOrderDerivatives.hpp#L42)

This results in systematic differences in rounding on both sides of the grid, and this error can build up surprisingly fast as we've seen - as we're essentially preferentially discarding the low bits of our floats but biased in a specific direction. Eliminating these systematic errors is important. You might think you can just rewrite this expression like this, by grouping equidistant cells:

```c++
float diff(const std::vector<float>& points, int idx, float scale)
{
    return ((points[idx - 2] - points[idx + 2]) + (-8 * points[idx - 1] + 8 * points[idx + 1])) / (12 * scale);
}
```

But, surprisingly, tests will show that this still returns the wrong answer. What gives?

## The C++ loophole

In this piece of code:

```c++
float v1 = a*b + c;

float v_mul = a*b;
float v2 = v_mul + c;
```

C++ encourages that $v_1 \neq v_2$. This rather surprising feature is known as floating point contraction, and there is no standardised way to disable it[^pragma]. Within an expression, the compiler is free to turn anything of the form $a*b + c$ into $\mathrm{fma}(a, b, c)$, which may be both faster and more precise. Unfortunately - in our case, it also causes our 'fixed' code to be rewritten as follows:

[^pragma]: There is a non standard pragma inherited from C, but CUDA does not implement this. Given that this article is focused on GPU programming, its a problem

```c++
float diff(const std::vector<float>& points, int idx, float scale)
{
    return ((points[idx - 2] - points[idx + 2]) + (fma(-8, points[idx - 1], 8 * points[idx + 1]))) / (12 * scale);
}
```

Compilers can and do make this transform, and the difference in the way that our terms are dealt with will also reintroduce numerical error. This can be fixed in one of two ways:

```c++
float diff_long(const std::vector<float>& points, int idx, float scale)
{
    float vm2 = points[idx - 2];
    float vp2 = -points[idx + 2];
    float vm1 = -8 * points[idx - 1];
    float vp1 = 8 * points[idx + 1];

    float v2 = lm2 + lp2;
    float v1 = vm1 + vp1;
    float top = v1 + v2;

    return top / (12 * scale);
}
```

The above ('long form') represents the general form of how to fix this, and shows how to disable this compiler optimisation where necessary

```c++
float diff_concise(const std::vector<float>& points, int idx, float scale)
{
    return ((points[idx - 2] - points[idx + 2]) + 8 * (points[idx + 1] - points[idx - 1])) / (12 * scale);
}
```

The concise version only works in our specific case for first derivatives - as the FMA that gets generated does not upset symmetry, and gives a 20% improvement in GPU-land over the long form version[^compiler]

Kreiss-Oliger must be fixed in the same fashion as `diff_long`, by explicit pairwise summation, and creating a bunch of of intermediate variables to impair the compiler's ability to generate FMAs

[^compiler]: This is at least partly due to compiler-itus, as compilers are much better at optimising within an expression, than across multiple expressions. Its a big part of the reason why I use code generation in these articles

## Fixing dirac

Another source of error is the way we've implement the dirac delta function - fixing this function is along the same lines as differentiation. We must ensure that the order of operations is exactly the same between the left side of the grid, and the right side of the grid. At the moment, we're integrating in *world* coordinates in floats, which can lead to representation issues as values are truncated differently. So we're going to swap to cell index based coordinates instead. I've also changed $\Delta$ to take in a fraction in the range $[0, 1]$

$$
\Delta_2^{(3)}(r_f, r_s) = \frac{1}{\pi (\frac{r_s}{2})^3}
\begin{align}
\begin{cases}
1 - \frac{3}{2} (2 r_f)^2 + \frac{3}{4} (2 r_f)^3 \;\; &\mathrm{for}\;\; 0 \leq 2 r_f \leq 1\\
\frac{1}{4}(2 - 2 r_f)^3 \;\; &\mathrm{for}\;\; 1 \leq 2 r_f \leq 2\\
0 & \mathrm{otherwise}
\end{cases}
\end{align}
$$

This means that $r_s$ is now the full size of the particle in world coordinates, and $r_f$ is a fraction from 0 to 1. Now we can redefine the integral in 3d from earlier:

$$\Delta_{\mathrm{best}}^{(3)} =  \int_{z_c - 0.5}^{z_c + 0.5} \int_{y_c - 0.5}^{y_c + 0.5} \int_{x_c - 0.5}^{x_c + 0.5} \Delta_2\left (\frac{\sqrt{(x - x_c^{\mathrm{idx}})^2 + (y - y_c^{\mathrm{idx}})^2 + (z - z_c^{\mathrm{idx}})^2}}{(\frac{r_s}{h})}, r_s \right ) dx dy dz$$

Where $x_c, y_c, z_c$ are the positions of the cells in integral cell-based coordinates, and their half offsets can be represented exactly. $x_c^{\mathrm{idx}}, y_c^{\mathrm{idx}}, z_c^{\mathrm{idx}}$ is the position of the particle, converted into those same cell based coordinates. This avoids the first set of numerical problems from earlier. Next up, we need to deal with the integration itself

### Trapezoidal integration

Implementing a fully symmetric trapezoidal method would be very tricky. For numerical integration, it has the [following definition](https://en.wikipedia.org/wiki/Trapezoidal_rule):

$$\int^b_a f(x) dx = \Delta x \left (\frac{f(x_0) + f(x_N)}{2} + \sum^{n-1}_{k=1} f(x_k)\right )$$

Luckily for $N=2$ - which is good enough - this is actually straightforward. As long as we evaluate the right hand side sum, and the left hand side sum separately, then add them together at the end - it'll be symmetric. More iterations would require an outside in iteration scheme with pairwise summation

This is what I implemented (in 1d, just repeat the integral in 3d):

```c++
template<typename T, typename U>
inline
auto integrate_1d_trapezoidal(const T& func, int n, const U& upper, const U& lower)
{
    using variable_type = decltype(func(U()));

    variable_type sum = 0;

    for(int k=1; k < n; k++)
    {
        auto coordinate = lower + k * (upper - lower) / n;

        auto val = func(coordinate);

        sum += val;
    }

    return ((upper - lower) / n) * (0.5f * (func(lower) + func(upper)) + sum);
}
```

Note that the returned value is carefully written to avoid problems

More importantly, the mass oscillates with a naive discretisation as a particle moves through the grid, and it introduces systematic errors

There are about ~10 points in total in this article where its possible to implement things incorrectly, which can rapidly lead to multiple rounding errors per-cell per-tick. This is the reason why its so important - if you do it wrong *everywhere*, then everything on one side of your grid will experience multiple non random bits of error relative to the other side of your grid every tick, which can lead to very unexpected results over time

# Interpolation

As a reminder, our geodesic equation is as follows:

$$\begin{align}
\frac{d u_i}{dt} &= - \alpha u^0 \partial_i \alpha + u_j \partial_i \beta^j - \frac{u_j u_k}{2 u^0} \partial_i \gamma^{jk}\\
u^0 &= \frac{\sqrt{1 + \gamma^{ij} u_i u_j}}{\alpha}\\
\end{align}
$$

At every step, we need to interpolate the positions of the ADM variables $\gamma_{ij}$, $\alpha$, and $\beta^i$ in order to evolve this, at our particle's position $x^i_p$. A naive trilinear interpolation will lead to the same issues talked about above: Luckily, this *is* quite easily fixable:

```c++
template<typename T
inline
auto function_trilinear(T&& func, v3f pos)
{
    using namespace single_source;

    v3f floored = floor(pos);
    pin(floored);
    v3f frac = pos - floored;
    pin(frac);

    v3i ipos = (v3i)floored;

    auto c000 = func(ipos + (v3i){0,0,0});
    auto c100 = func(ipos + (v3i){1,0,0});

    auto c010 = func(ipos + (v3i){0,1,0});
    auto c110 = func(ipos + (v3i){1,1,0});

    auto c001 = func(ipos + (v3i){0,0,1});
    auto c101 = func(ipos + (v3i){1,0,1});

    auto c011 = func(ipos + (v3i){0,1,1});
    auto c111 = func(ipos + (v3i){1,1,1});

    auto lmix = [&](auto& a, auto& b, auto& t)
    {
        auto imx = no_opt(1-t);
        auto imimx = no_opt(1-imx);

        auto p1 = no_opt(imx * a);
        auto p2 = no_opt(imimx * b);

        return no_opt(p1 + p2);
    };

    auto c00 = lmix(c000, c100, frac.x());
    auto c01 = lmix(c010, c110, frac.x());

    auto c10 = lmix(c001, c101, frac.x());
    auto c11 = lmix(c011, c111, frac.x());

    auto c0 = lmix(c00, c01, frac.y());
    auto c1 = lmix(c10, c11, frac.y());

    return lmix(c0, c1, frac.z());
}
```

Note that `no_opt` in the scheme I'm using forces a variable declaration, to disable fp contraction. `lmix` guarantees the property:

$$\mathrm{lmix}(a, b, t) == \mathrm{lmix}(b, a, 1-t)$$

Trilinear interpolation is otherwise a very standard algorithm, and not worth diving into. In many situations, trilinear interpolation is perfectly fine, but we'll have to go into when it is not

## Symmetric tricubic interpolation

The next step up from trilinear interpolation, is tri*cubic* interpolation. I'll just put this out there: Everyone does cubic interpolation wrong. Its common to use hermite[^hermite] interpolation - this kind of interpolation guarantees the values of the derivatives at our boundaries. We don't differentiate our interpolated variables nor do we care about its derivatives, so this is a bad move for us

[^hermite]: Wikipedia will direct you to [this](https://citeseerx.ist.psu.edu/viewdoc/summary?doi=10.1.1.89.7835) paper, which is precisely the wrong approach. Its set up to be able to repeatedly perform hermite interpolation with the same set of values, which is not what we want at all

What we want is tricubic Lagrangian interpolation, via a Lagrange interpolating polynomial. This does not require us to know the values of the derivatives anywhere, and its both faster and more accurate than hermite interpolation. It does have the downside that I now have to do more work though

### Cubic Lagrangian interpolation

The minimum number of points to do cubic interpolation is $4$. We'll operate in grid cells, which means that we have the following node structure:

| Node label | $x_0$ | $x_1$ | $x_2$ | $x_3$
|-|-|-|-|-|
|Value|$-1$|$0$|$1$|$2$|

A cubic interpolating polynomial is constructed as follows (all bounds are inclusive):

$$\begin{align}
l_j = \prod_{m=0, m \neq j}^3 \frac{x - x_m}{x_j - x_m}\\
L(x) = \sum^3_{j} f_j l_j(x)\\
\end{align}
$$

$f_j$ represents the function value at the grid cell corresponding to the node. $x$ here is in the range $[0, 1]$, and represents the fractional offset of a particle's position with respect to the grid cells

A 3d polynomial can be constructed as follows:

$$L(x, y, z) = \sum^3_a \sum^3_b \sum^3_c f_{abc} l_a(x) l_b(y) l_c(z)$$

This is a large sum of 64 values. As you may have, you can't implement this as written otherwise we'll end up with massive systematic rounding errors. We instead have to perform a pairwise matched summation of all values, to ensure exactly the same order of operations on both sides of the grid

#### Simple but wrong

This is tricubic interpolation without any corrections for floating-point-itus

```c++
template<typename T, typename... U>
inline
auto tricubic_particles(T&& func, v3f frac, v3i ifloored, U&&... args)
{
    using namespace single_source;

    std::array<float, 4> nodes = {
        -1,
        0,
        1,
        2
    };

    using value_v = decltype(func(v3i(), std::forward<U>(args)...));

    auto L_j = [&](int j, const valuef& f, float& bottom_out)
    {
        int bottom = 1;

        valuef out = 1;

        for(int m=0; m < 4; m++)
        {
            if(m == j)
                continue;

            bottom = bottom * (nodes[j] - nodes[m]);

            out = out * (f - nodes[m]);
        }

        bottom_out = (float)bottom;

        return out;
    };

    value_v sum = {};

    for(int z=0; z < 4; z++)
    {
        for(int y=0; y < 4; y++)
        {
            for(int x=0; x < 4; x++)
            {
                v3i offset = (v3i){x - 1, y - 1, z - 1};

                auto u = func(ifloored + offset, std::forward<U>(args)...);
```

#### Complex but correct

This is the pairwise matched summation version of the above. GPU loops are emitted instead of unrolled, as AMD appears to suffer when too many memory accesses are emitted

```c++
template<typename T, typename... U>
inline
auto tricubic_particles(T&& func, v3f frac, v3i ifloored, U&&... args)
{
    using namespace single_source;

    using value_v = decltype(func(v3i(), std::forward<U>(args)...));

    //I accumulate the top, and bottom portions of the lagrange interpolating polynomial basis functions separately
    //as the bottom is a collection of integral constants
    auto L_j = [&](valuei j, const valuef& f, mut<valuef>& bottom_out)
    {
        //evaluate a basis function
        auto apply_for_m = [&](int m)
        {
            mut<valuef> out = declare_mut_e(valuef(1));

            if_e(m != j, [&]{
                //node locations are implicitly calculated as label - 1
                as_ref(bottom_out) = declare_e(bottom_out) * ((valuef)j - 1.f - ((float)m - 1));

                as_ref(out) = (f - (valuef)(m - 1));
            });

            return declare_e(out);
        };

        return (apply_for_m(0) * apply_for_m(3)) * (apply_for_m(1) * apply_for_m(2));
    };

    auto sum = declare_mut_e(value_v());

    auto fetch_indices = [](valuei what)
    {
        return ternary(what == 0, (v2i){0,3}, (v2i){1, 2});
    };

    mut<valuei> iz = declare_mut_e(valuei());

    for_e(iz < 2, assign_b(iz, iz+1), [&]{
        mut<valuei> iy = declare_mut_e(valuei());

        for_e(iy < 2, assign_b(iy, iy+1), [&]{
            mut<valuei> ix = declare_mut_e(valuei());

            for_e(ix < 2, assign_b(ix, ix+1), [&]{
                auto xs = fetch_indices(declare_e(ix));
                auto ys = fetch_indices(declare_e(iy));
                auto zs = fetch_indices(declare_e(iz));

                //evaluates the interior term of the sum
                auto eval_for = [&](valuei x, valuei y, valuei z)
                {
                    v3i offset = (v3i){x - 1, y - 1, z - 1};

                    auto u = func(ifloored + offset, std::forward<U>(args)...);

                    mut<valuef> bx = declare_mut_e(valuef(1));
                    mut<valuef> by = declare_mut_e(valuef(1));
                    mut<valuef> bz = declare_mut_e(valuef(1));

                    auto val = no_opt(u * L_j(x, frac.x(), bx) * L_j(y, frac.y(), by) * L_j(z, frac.z(), bz));

                    return no_opt(val * (1/(declare_e(bx) * declare_e(by) * declare_e(bz))));
                };

                auto v000 = eval_for(xs[0], ys[0], zs[0]);
                auto v100 = eval_for(xs[1], ys[0], zs[0]);

                auto v010 = eval_for(xs[0], ys[1], zs[0]);
                auto v110 = eval_for(xs[1], ys[1], zs[0]);

                auto v001 = eval_for(xs[0], ys[0], zs[1]);
                auto v101 = eval_for(xs[1], ys[0], zs[1]);

                auto v011 = eval_for(xs[0], ys[1], zs[1]);
                auto v111 = eval_for(xs[1], ys[1], zs[1]);

                auto v00 = v000 + v100;
                auto v10 = v010 + v110;
                auto v01 = v001 + v101;
                auto v11 = v011 + v111;

                auto v0 = v00 + v10;
                auto v1 = v01 + v11;

                as_ref(sum) += (v0 + v1);
            });
        });
    });

    return declare_e(sum);
}
```

# Initial conditions

There are three components to the initial conditions:

1. Define the particle's 4-velocity
2. Solve the hamiltonian constraint
3. Possibly solve the momentum constraint

## 4-velocity

Here, velocity is defined relative to the inertial frame of reference of the particle. This means that to calculate the 4-velocity, we need to first construct a tetrad. While in the general case you'll need to [Gram-Schidt](https://en.wikipedia.org/wiki/Gram%E2%80%93Schmidt_process) the metric to find a set of tetrads (eg see [here](https://20k.github.io/c++/2024/06/19/tetrads.html)), our initial conditions will always produce a diagonal metric - which makes tetrad construction straightforward

Firstly, take the following initial slice: $\alpha = 1, \beta^i = 0$. Then, we can construct the metric tensor as follows:

$g_{\mu\nu} =$

||0|1|2|3|
|-|-|-|-|-|
|0|-1| | | |
|1|  |$\gamma_{00}$| | |
|2|  |  |  $\gamma_{11}$| |
|3|  |  |  | $\gamma_{22}$ |

This gives the tetrads via the usual relation for diagonal metrics (ie [1.4.21](https://arxiv.org/pdf/0904.4184)):

$$\begin{align}
e_0^0 &= 1\\
e_1^1 &= \frac{1}{\sqrt{\gamma_{00}}}\\
e_2^2 &= \frac{1}{\sqrt{\gamma_{11}}}\\
e_3^3 &= \frac{1}{\sqrt{\gamma_{22}}}\\
\end{align}$$

The lower index labels the tetrad vector, and the upper index labels the coordinate. From here, you first construct a 4-velocity locally, and then use the tetrad to find the global 4-velocity:

$$\begin{align}
\gamma &= \frac{1}{\sqrt{1 - \mid v \mid^2}}\\
v_{flat}^{\mu} &= \gamma(1, v_0, v_1, v_2)\\
v_{curved}^\mu &= e_i^\mu v_{flat}^i
\end{align}$$

Note that the $i$ index runs from $0$ to $4$ contrary to the rest of this article, as this is standard notation for tetrads[^notthesame]. $v_{curved}$ is the final velocity of the particle

[^notthesame]: This use of index notation isn't really the same as other uses, as the lower index of a tetrad is only denoting the label of which vector you're talking about (rather than it having co and contravariant indices). Tetrad indices when inverted correspond to a matrix inversion (when treating the tetrad vectors as the column vectors of a 4x4 matrix), and does not involve the metric tensor

## Hamiltonian constraint solving

Its important to solve the hamiltonian constraint as part of the initial conditions, because errors here are quite sticky, and can leave visual 'welts' on your simulation that are very noticeable. The hamiltonian constraint that we'll be using can be derived from [2.11](https://arxiv.org/pdf/1905.08890), and with the standard set of constraints looks like this:

$$
\nabla \psi = - \psi^{-7} \bar{A}_{ij} \bar{A}^{ij} - 2 \pi \psi^5 \rho_H
$$

$\rho_H$ is the source term for the stress-energy tensor, and I'm keeping the same notation from the matter article. To keep solving, we need two things:

1. $\rho_H$ (the scalar source term for the stress-energy tensor)
2. $\bar{A}_{ij}$ (the extrinsic curvature)

### $\rho_H$

We already know that:

$$\rho_H = \alpha W^3 \sum m u^0 \delta^{(3)}(x^i - x^i_{\mathrm{p}})$$

The only issue is that we don't have a value of $W$ that we can use (we'll implicitly set $\alpha = 1$). To solve this, we know that:

$$\begin{align}
\bar{\gamma}_{ij} \psi^4 &= \gamma_{ij}\\
\tilde{\gamma}_{ij} &= W^2 \gamma_{ij}\\
\end{align}
$$

Apply the rules of determinants:

$$\begin{align}
det(\bar{\gamma}_{ij} \psi^4) &= det(\gamma_{ij}) = det(\tilde{\gamma}_{ij} W^{-2})\\
(\psi^4)^3 &= (W^{-2})^3\\
\psi^{12} &= W^{-6}\\
\psi^{-6} &= W^3\\
\end{align}
$$

Lets now define $\bar{\rho}_H = \sum m u^0 \delta^{(3)}(x^i - x^i_{\mathrm{p}})$, ie dropping the conformal factor (and setting $\alpha=1$). This means you may rewrite the hamiltonian constraint as this:

$$\nabla \psi = - \psi^{-7} \bar{A} _{ij} \bar{A}^{ij} - 2 \pi \psi^{-1} \bar{\rho}_H$$

This is actually solvable, aside from $\bar{A}_{ij}$. To figure that out, we'll dip into the momentum constraint

## $\bar{A}_{ij}$ and the momentum constraint

When our particles are not moving, $\bar{A}_{ij} = 0$ - and bob's your uncle. All particle papers I have looked at use stationary particles, and it seems like nobody wants to touch this problem with a 100ft barge pole. As a professional barge pole toucher, this question has been haunting me for a while

One approach is to repurpose the [neutron star](https://arxiv.org/pdf/1606.04881) initial conditions paper - set the pressure to $0$, and to model a body without spin. When an object does not have spin, the solution becomes spherically symmetric. The reduced problem is as follows:

$$\begin{align}
\bar{A}^{ij} &= \frac{3Q}{2r^2}(P^i l^j + P^j l^i - (\eta^{ij} - l^i l^j) P_i l^i)\\
Q &= \int^r_0 4 \pi \sigma(x) x^2 dx\\
\sigma(x) &= \frac{\tilde{\rho}_H}{\mathcal{M}}\\
\mathcal{M} &= 4 \pi \int^{r_0}_0 \tilde{\rho}_H r^2 dr\\
\end{align}$$

Strictly speaking, this is approximate - as it assumes that $W$ is constant within the body, and so disappears in the normalisation factor $\mathcal{M}$. Tests show that this reduces the momentum constraint violations significantly. This isn't worth solving for the following reasons:

1. Generally we're dealing with relatively low velocity particles, so $\bar{A}_{ij} \approx 0$ anyway
2. All formalisms are momentum constraint damped, so errors disappear quickly
3. It involves summing across all particles over all points of the grid, which is very bad perf-wise. In general you'll likely want to merge nearby particles, and perform other grouping approximations which are non trivial

I've bundled an implementation of this in with the article, but its switched off by default. Because it has minimal value, I'm not going to dig into this more

## Calculating the stress-energy tensor

This is the bit which is much more interesting. I think I've finally come up with a decent approach here, which is free of the limitations of older methods I've explored in the past

The basic idea is as follows:

1. Loop over the size (in cells) of the particle, determined by the dirac delta size
2. Accumulate the stress energy tensor on the grid directly, using 64-bit fixed point

In the past, I've tried multiple difference techniques here. While using atomics may seem suboptimal, other techniques have downsides which are discussed at the end of the article

### Looping over the size in cells of the particle

Instead of defining the size of a particle in world coordinate, I do it in cells - and calculate the radius in world coordinates of the particle. This gets plugged into the dirac delta function (which remember: we modified the definition of to take a unit fraction)

This gives a simple loop procedure:

```c++
void for_each_dirac(v3i dim, valuef scale, v3f dirac_pos, int radius_cells, auto&& func)
{
    using namespace single_source;
    assert(radius_cells > 0);

    v3f fpos = world_to_grid(dirac_pos, dim, scale);

    v3i cell = (v3i)floor(fpos);
    pin(cell);

    //The appropriate modification is rightwards + 1, leftwards + 0
    int spread = radius_cells + 1;

    mut<valuei> z = declare_mut_e(valuei(-radius_cells));

    for_e(z <= spread, assign_b(z, z+1), [&]{
        mut<valuei> y = declare_mut_e(valuei(-radius_cells));

        for_e(y <= spread, assign_b(y, y+1), [&]{
            mut<valuei> x = declare_mut_e(valuei(-radius_cells));

            for_e(x <= spread, assign_b(x, x+1), [&]{
                v3i offset = {declare_e(x), declare_e(y), declare_e(z)};
                offset += cell;
                pin(offset);

                valuef dirac = integrate_dirac_gpu(dirac_delta<valuef>, (v3f)offset, fpos, radius_cells, scale);
                pin(dirac);

                if_e(dirac > 0, [&]{
                    func(offset, dirac);
                });
            });
        });
    });
}
```

The interesting parts here are:

1. `dirac_pos` is just the particle position
2. The cells that the dirac delta function covers must be offset by one in the *rightwards* direction only, as its origin can take fractional positions
3. These loops are not unrolled on the GPU, as it causes very bad performance issues
4. Many of the cells are simply skipped. It would be a lot more efficient to somehow directly iterate over a sphere, than a cube

### Accumulation

This is one of the most critical kernels in the entire program, so I'm going to parse out the interesting bits here:

```c++
void calculate_particle_intermediates(execution_context& ectx,
                                      particle_base_args<buffer<valuef>> particles_in,
                                      buffer<valuef> lorentz_in,
                                      particle_utility_args<buffer_mut<valuei64>> out,
                                      literal<v3i> dim, literal<valuef> scale, literal<value<size_t>> particle_count,
                                      literal<valued> fixed_scale, int radius_cells)
{
    using namespace single_source;

    value<size_t> id = value_impl::get_global_id_us(0);
    pin(id);

    if_e(id >= particle_count.get(), [&]{
        return_e();
    });

    valuef lorentz = lorentz_in[id];
    valuef mass = particles_in.get_mass(id);
    v3f pos = particles_in.get_position(id);
    v3f vel = particles_in.get_velocity(id);

    pin(pos);
    pin(vel);
    pin(mass);
    pin(lorentz);

    if_e(!isfinite(mass) || mass == 0, [&]{
        return_e();
    });

    for_each_dirac(dim.get(), scale.get(), pos, radius_cells, [&](v3i offset, valuef dirac) {
        valuef E = mass * lorentz * dirac;
        v3f Ji = mass * vel * dirac;

        tensor<valuef, 3, 3> Sij;

        for(int i=0; i < 3; i++)
        {
            for(int j=0; j < 3; j++)
            {
                Sij[i, j] = (mass * vel[i] * vel[j] / lorentz) * dirac;
            }
        }

        std::array<valuef, 6> Sij_sym = extract_symmetry(Sij);

        auto scale = [&](valuef in)
        {
            valued in_d = (valued)in;
            valued in_scaled = in_d * fixed_scale.get();

            return (valuei64)round((valuef)in_scaled);
        };

        valuei64 E_scaled = scale(E);

        tensor<valuei64, 3> Si_scaled;

        for(int i=0; i < 3; i++)
            Si_scaled[i] = scale(Ji[i]);

        std::array<valuei64, 6> Sij_scaled;

        for(int i=0; i < 6; i++)
            Sij_scaled[i] = scale(Sij_sym[i]);

        valuei idx = offset.z() * dim.get().y() * dim.get().x() + offset.y() * dim.get().x() + offset.x();

        valuei64 val = out.E.atom_add_e(idx, E_scaled);

        //basic overflow detection, as E > 0
        if_e(val < 0, [&]{
            print("Error in particle dynamics\n");
        });

        for(int i=0; i < 3; i++)
            out.Si_raised[i].atom_add_e(idx, Si_scaled[i]);

        for(int i=0; i < 6; i++)
            out.Sij_raised[i].atom_add_e(idx, Sij_scaled[i]);
    });
}
```

You might notice that the fixed point scaling is handled as follows:

There's an extra intermediate rounding to `float` (`valuef`) which may seem strange. Its unfortunately a significant performance win to do this (I don't know why - possibly because AMD's handling of the maths library can be odd), which means that we have to check if this step is rigorously well founded. The calculation of the scale factor for fixed point is therefore critical for accuracy

#### Fixed point scale factor

There are two primary concerns with calculating the fixed point scale factor:

1. As much accuracy as possible is good
2. The simulation must be able to tolerate a significant overlap of particle contributions without overflowing

The largest, most significant term is $E$, which has the form `mass * lorentz * dirac`. Given that `dirac` maxes out at $1$, and `lorentz` $\approx 1$, I assume that the maximum contribution of a particle to a cell is roughtly `mass`

That means that for a single particle, if you set the fixed point to be $F = \frac{K}{mass}$, the resulting integral value will have a value of approximately $K$. So in total, this means that you can easily define:

```c++
double get_fixed_scale(double total_mass, int64_t particle_count)
{
    double fixed_scale = ((double)particle_count / total_mass) * pow(10., 7.);
    return fixed_scale;
}
```

This means that each particle gets $10^7 \approx 2^{12}$ bits of precision per cell, and each cell can hold $\approx 2^{64-12}$ dirac samples. This also gives a lot of headroom, while providing adequate precision. Note that the number of dirac samples far exceeds the number of particles, as each particle overlaps multiple cells

I list a transparent performance improvement to this scheme at the end of this article

#### Fixed point -> Float

To actually consume the data in the BSSN kernel, I convert the 64-bit fixed point back into floats as a separate pass via a simple division. This uses a bit more memory, and could probably be eliminated or done in place

## An optional performance improvement

Particles have their properties stored in a big linear buffer. This means that, assuming particles are distributed randomly, memory is accessed randomly when accumulating particle data and performing the evolution kernels

One fix for this is to perform a partial sorting, to group particles in the same cell together in memory. I do this via a simple slab allocator, which has excellent performance characteristics

```c++

void count_particles_per_cell(execution_context& ectx, std::array<buffer<valuef>, 3> pos, buffer_mut<valuei> cell_counts, literal<v3i> dim, literal<valuef> scale, literal<value<size_t>> particle_count)
{
    using namespace single_source;

    value<size_t> id = value_impl::get_global_id_us(0);
    pin(id);

    if_e(id >= particle_count.get(), [&]{
        return_e();
    });

    v3f world_pos = {pos[0][id], pos[1][id], pos[2][id]};
    pin(world_pos);

    v3f grid_posf = world_to_grid(world_pos, dim.get(), scale.get());
    pin(grid_posf);
    v3i grid_pos = (v3i)floor(grid_posf);

    grid_pos = clamp(grid_pos, (v3i){0,0,0}, dim.get() - 1);

    valuei idx = grid_pos.z() * dim.get().x() * dim.get().y() + grid_pos.y() * dim.get().x() + grid_pos.x();

    cell_counts.atom_add_e(idx, 1);
}

void memory_allocate(execution_context& ectx, buffer_mut<valuei> counts, buffer_mut<valuei> memory_ptrs, buffer_mut<valuei> memory_allocator, literal<valuei> work_size)
{
    using namespace single_source;

    valuei id = value_impl::get_global_id(0);
    pin(id);

    if_e(id >= work_size.get(), [&]{
        return_e();
    });

    valuei my_count = counts[id];

    mut<valuei> my_memory = declare_mut_e(valuei(0));

    if_e(my_count > 0, [&]{
        as_ref(my_memory) = memory_allocator.atom_add_e(valuei(0), my_count);
    });

    as_ref(memory_ptrs[id]) = declare_e(my_memory);
    as_ref(counts[id]) = valuei(0);
}

void permute_memory(execution_context& ectx, particle_base_args<buffer<valuef>> in, particle_base_args<buffer_mut<valuef>> out, buffer_mut<valuei> memory_ptrs, buffer_mut<valuei> cell_counts, literal<v3i> dim, literal<valuef> scale, literal<value<size_t>> particle_count)
{
    using namespace single_source;

    value<size_t> id = value_impl::get_global_id_us(0);

    if_e(id >= particle_count.get(), [&]{

    });

    v3f world_pos = in.get_position(id);

    valuei cell_offset = memory_ptrs[idx];
    pin(cell_offset);

    valuei idx_out = my_offset + cell_offset;

    for(int i=0; i < 3; i++)
    {
        as_ref(out.positions[i][idx_out]) = in.positions[i][id];
        as_ref(out.velocities[i][idx_out]) = in.velocities[i][id];

}
```

# C++ is sometimes a very poor numerical language

In C++, it is impossible to implement a type that behaves exactly like a `float`. This was a surprising fact to me when I discovered it - for a language that sells itself as having zero overhead, this is a strange omission. To take a simple example, let's have a look at the following two pieces of code:

```c++
float func_1(float a, float b, float c)
{
    return a * b + c;
}

float func_2(float a, float b, float c)
{
    float mul = a*b;
    return mul + c;
}
```

I suspect that most people are not aware that these two pieces of code are strictly non equivalent in C/C++. This isn't a theoretical problem either, if you compile these two functions you'll discover that they really do generate different assembly, and return different results. This isn't an IEEE float thing, this is just pure C++-itus

C++ allows *expressions* to have what is called floating point contraction applied to them. This means that `a * b + c` is legally allowed to be transformed to `fma(a, b, c)`, and evaluated in higher precision implicitly. Because in `func_2` they're two separate expressions, this optimisation is not allowed. This might seem like a minor problem - most of the time we don't actually care - but today its going to cause us severe problems

## Sources of asymmetry

Tracking this down can be a pain, and this article is going to be very pedantic about IEEE. Before we even get to the particle dynamics, there are three major sources of asymmetry that can perturb a simulation:

1. Derivative calculations
2. Kreiss-Oliger
3. The initial conditions laplace solver

To illustrate the problem, we're using 4th order derivatives. A seemingly sane sensible person implements it something like this:

```c++
float diff(const std::vector<float>& points, int idx, float scale)
{
    return (points[idx - 2] - 8 * points[idx - 1] + 8 * points[idx + 1] - points[idx + 2]) / (12 * scale);
}
```


How this could introduce asymmetry is straightforward: compilers interpret these expressions left to right, and so we get the following expression:

```c++
(((points[idx - 2] - 8 * points[idx - 1]) + 8 * points[idx + 1]) - points[idx + 2])
```

The rounding here is asymmetric with respect to `idx`. If we have a central grid point about which our data is mirrored, say $10$, we want the evaluation of $idx = 9$ and $idx = 11$ to return *exactly* the same results. Plugging that in, we get the following:


Substituting this through will show that its all hunky dory. The only problem now is that we have to deal with C++-itus, as the right hand side will get transformed to `fma(-8, points[idx-1], 8 * points[idx + 1])`. So instead of the simple solution, the pedantically correct version of this is as follows:

```c++
float diff(const std::vector<float>& points, int idx, float scale)
{
    float vm2 = points[idx - 2];
    float vp2 = -points[idx + 2];
    float vm1 = -8 * points[idx - 1];
    float vp1 = 8 * points[idx + 1];

    float v2 = lm2 + lp2;
    float v1 = vm1 + vp1;
    float top = v1 + v2;

    return top / (12 * scale);
}
```

The above ('long form') represents the general form of how to fix this, and shows how to disable this compiler optimisation where necessary. For the specific case of first derivatives, the below also works - as the FMA that gets generated does not upset symmetry. This is a 20% improvement in GPU-land over the above[^compiler]

[^compiler]: This is at least partly due to compiler-itus, as compilers are much better at optimising within an expression, than across multiple expressions. Its a big part of the reason why I use code generation in these articles

```c++
float diff(const std::vector<float>& points, int idx, float scale)
{
    return ((points[idx - 2] - points[idx + 2]) + 8 * (points[idx + 1] - points[idx - 1])) / (12 * scale);
}
```

Kreiss-Oliger is fixed in the long form fashion

## Floating point symmetric interpolation

Todo: Move this into trilinear/tricubic

During our initial conditions, we have to implement linear interpolation for the upscaling step - and you might think to reach for `std::lerp`. If you go read through the spec, you'll discover that a lot of work was put into it to make it work well. Unfortunately, it is inappropriate for our use case: it does not guarantee the following property:

```c++
std::lerp(a, b, t) = std::lerp(b, a, 1-t)
```

I know this seems like we're messing about in the weeds, but these errors compound over time. The correct way in theory to implement *exactly* symmetric linear interpolation for us is as follows:

```c++
float interpolate(float a, float b, float t)
{
    return (1-t) * a + (1-(1-t)) * b;
}
```

For this to be actually correct we have to work around floating point contraction:

```c++
float interpolate(float a, float b, float t)
{
    float imx = 1-t;
    float imimx = 1-imx;

    float p1 = imx * a;
    float p2 = imimx * b;

    return p1 + p2;
}
```

The laplacian also suffers from the same problem as Kreiss-Oliger and the derivatives, and can be solved in the same fashion. You should also be aware: for a value $x$ representing a grid cell which can have a fractional component, the value $d_x - x - 1$ likely cannot be represented exactly enough. You'll either have to split your values into an integral component representing the cell, and a fractional component representing the offset within it - or store your floats in the range $[-(d_x-1)/2, (d_x-1)/2]$ (for odd grid cell sizes) instead of the range $[0, d_x - 1]$ as is more traditional

## Takeaways

This is my least favourite part of the C++ spec, as it severely complicates a lot of code. While some compilers support simply disabling FP contraction, its hugely important for performance on the GPU in some cases. Importantly, CUDA **does not** implement the pragma required (as it is not officially part of the C++ spec), and GPU compilers love FMAs

This issue causes bugs in real-world code, eg [here's](https://github.com/GRTLCollaboration/GRChombo/blob/130140afe972701575740685343ea28f6ab8234c/Source/BoxUtils/FourthOrderDerivatives.hpp#L42) one example of a numerical relativity toolkit which falls into the double whammy trap of both incorrect ordering of operations, and floating point contraction. The joys!

I have never seen a single discussion of this anywhere. There are some extremely cryptic references to this problem in the literature: many simulations run in a symmetry mode, where the simulation grid is chopped in half (or 8ths) and implicitly mirrored to cut down on simulation costs - there are reports that the simulation for unknown reasons is more stable when running in a mirrored mode, vs a non mirrored mode (which is presumably implicitly symmetric). You can probably see that a systematic asymmetry being applied over a long running simulation has the potential to cause an upset

The code bundled with this article has been updated and checked to make sure this problem isn't present

# Equations

Its time to change tack, and go check out the equations we'll be using today. There are three sets of equations to pick from:

1. The [ADM geodesic equations (12-13)](https://arxiv.org/pdf/1611.07906), which you may remember from the rendering article
2. A scheme based on [4-momentum (2.27)](https://arxiv.org/pdf/1904.07841)
3. A scheme based on the [4-velocity (2.9)](https://scispace.com/pdf/3d-numerical-simulation-of-black-hole-formation-using-43u5c2u959.pdf)

The third formalism is by far the best and that's what we'll be using, for the following reasons:

1. It does not involve the extrinsic curvature $\tilde{A}_{ij}$ compared to #1, which is hugely good for performance. There are also only three evolution equations vs 4
2. The 4-momentum is a poor choice of evolution variable. We'll be dealing with particles with extremely tiny masses, so with an extremely small 4-momentum, the velocity will be very inaccurate

Given a 4-velocity $u^\mu$, the spatial components $u_i$ are evolved as follows:

$$\begin{align}
\frac{d u_i}{dt} &= - \alpha u^0 \partial_i \alpha + u_j \partial_i \beta^j - \frac{u_j u_k}{2 u^0} \partial_i \gamma^{jk}\\
u^0 &= \frac{\sqrt{1 + \gamma^{ij} u_i u_j}}{\alpha}\\
\end{align}
$$

The particle's position is evolved as follows (via $\frac{dx^i}{dt} = \frac{u^i}{u^0}$):

$$
\frac{dx^i}{dt} = -\beta^i + \frac{\gamma^{ij} u_j}{u^0}
$$

This formalism  also has the advantage of being very simple, and is derived directly from the geodesic equation: $u^\mu \nabla_\mu u_\nu = 0$. So far, so good

Note: You'll need to interpolate the quantities (eg the metric, and $\beta^j$) above based on the position $x^i$. I'll get into how to do this later

## Source terms

Matter interacts with the metric in general relativity via the stress-energy tensor. The 4d stress energy tensor for a single particle labelled by $\mathrm{idx}$ is (2.5):

$$
T_{\mu\nu}^{\mathrm{idx}} = m_{\mathrm{idx}} \alpha^{-1} W^3 \delta^{(3)}(x^i - x_{\mathrm{idx}}^i)\frac{u_\mu^\mathrm{idx} u_\nu^\mathrm{idx}}{u_\mathrm{idx}^0}\\
$$

You simply sum the stress energy tensors for every particle, ie $$T_{\mu\nu}^{\mathrm{full}} = \sum^N_{\mathrm{idx} = 1} T_{\mu\nu}^{\mathrm{idx}}$$

|Symbol | Meaning |
|-|-|
|$m_{\mathrm{idx}}$ | The rest mass of a particle |
|$\alpha$ | Lapse, evaluated at $x^i$ |
| $W$ | Conformal factor, evaluated at $x^i$ |
| $\delta^{(3)}(x)$ | The 3d dirac delta function. This a very non trivial term, and there's a whole section dedicated just to this |
| $x^i$ | The current coordinate position you're looking at |
| $x^i_{\mathrm{idx}}$ | The position of the particle |
| $u^{\mathrm{idx}}_\mu$ | The 4-velocity of a particle, lowered |
| $u^0_{\mathrm{idx}}$ | The 0th component of the 4-velocity of a particle, which is additionally the Lorentz factor. Calculating this must use interpolated quantities at $x^{i}_{\mathrm{idx}}$, not $x^i$ |

### Projected source terms

We can't directly plug the stress energy tensor in however, as we need the ADM projections of the stress energy tensor $T^{\mathrm{idx}}_{\mu\nu}$. These are (2.14, 2.15, 2.20):

$$
\begin{align}
\rho_H &= m u^0 \alpha W^3 \delta^{(3)}(x^i - x^i_{\mathrm{idx}})\\
S_i &= m u_i W^3 \delta^{(3)}(x^i - x^i_{\mathrm{idx}})\\
S_{ij} &= m \frac{u_iu_j}{u^0} \alpha^{-1} W^3 \delta^{(3)}(x^i - x^i_{\mathrm{idx}})\\
\end{align}
$$

These are summed across all particles

#### An oddity in the literature

One thing to note is that in the literature, when performing the ADM projection of your velocity (which we don't do), you end up with something like:

$$u^\mu = \Gamma(n^\mu + V^\mu)$$

$\Gamma$ is sometimes called a lorentz factor (or, in a similar decomposition: energy). Setting $^\mu=0$, you get:

$$u^0 = \frac{\Gamma}{\alpha}$$

This was quite confusing to me for a while, as you end up different equations for the stress-energy tensor, and $\Gamma$ is not directly the lorentz factor

# The Dirac Delta Function $\delta$ is the final boss of C++/IEEE

The dirac delta function has a very obtuse and non useful definition:

$$\delta(x) =
\begin{align}
\begin{cases}
0, \; &x \neq 0 \\
\infty, \; &x = 0
\end{cases}
\end{align}
$$

The slightly more useful definition of the dirac delta function is as follows:

$$\int^\infty_{-\infty} \delta(x) \; dx = 1$$

This is the key property of the dirac delta function. It has an integral of $1$, and yet it only applies to a single infinitesimal point, with no area. This may seem very curious, but take the example a pointlike particle's contribution to gravity. We know that it has infinitesimal extent as it is pointlike, and so where it interacts with the stress energy tensor must also be an infinitesimal area

This still seems clearly absurd, but the maths works out - and its often described more as an integration trick. People will frequently say, you never actually need to implement this, because it'll disappear. Unfortunately, ours doesn't, and how it is implemented is frequently on some quite shakey grounds

## Implementing the dirac delta function

Numerically, its clear that this function is unworkable. So instead, we want to implement something that approximates the dirac delta function - in essence, you smear it out over a small area. Todo: diagram. We might demand that this new function has a few properties:

1. It is compactly supported, ie it has finite extent
2. It is smooth-ish
3. This function has an integral of 1

Lets examine a basic dirac delta discretisation, as a triangle:

$$\Delta(x) =
\begin{align}
\begin{cases}
1 - x, \; &\mid x\mid < 1 \\
0, \; \mathrm{otherwise}
\end{cases}
\end{align}
$$

This function spans the range $-1$ to $1$. The integral of $1-x$ from $0$ to $1$ is $0.5$, so its area is correct. This is a valid, albeit not very smooth, discretisation

## Low grid resolutions

One of the things we most want with the dirac delta function - when discretised - is to preserve the *volume*. That means that this sum:

$$\sum_1^n \Delta(x_n) \; h$$

Should evaluate to exactly $1$, where $h$ is the grid spacing. Now, our naive discretisation like this doesn't actually guarantee that - it only guarantees in the limit as $h \mathrel{-}> 0$. The accuracy of our integral is dependent on the size of the dirac delta discretisation having a sufficient number of grid cells, but the accuracy of our simulation goes down as the number of grid cells covered by the discretisation goes up (as it less accurately approximates the dirac delta function)

Given that a larger dirac discretisation is both less accurate (we're approximating something pointlike!), and will be our #1 performance constraint, making this as precise as possible is very important

The remedy is to calculate the exact amount of the dirac delta function that intersects with our cell. We can do this by integrating:

$$\sigma = \frac{\int_{x - \frac{h}{2}}^{x + \frac{h}{2}} \Delta(y) dy}{h}$$

Where $y$ is our integration variable between the bounds $x - \frac{dx}{2}$ and $x + \frac{dx}{2}$. This leads to an exact conservation of the dirac delta, and the difference can be quite significant. More importantly, it eliminates systematic sampling errors, which is always a strong problem

This also generalises to $n$ dimensions - in 3d:

$$\sigma = \frac{\int_{z - \frac{h}{2}}^{z + \frac{h}{2}} \int_{y - \frac{h}{2}}^{y + \frac{h}{2}} \int_{x - \frac{h}{2}}^{x + \frac{h}{2}} \Delta(x, y, z) dx dy dz}{h^3}$$

## Of course, its not that simple

In the equation above, $x,y,z$ represent world coordinates of our cell's coordinate position, *not* grid cell coordinates. This means that we will be integrating between arbitrary bounds represented in floating point - and our results won't be symmetric. Eg, if our world is $30$ wide, $h = 0.1$ , and we're looking at two world points at $1$ and $29$, integrating from $0.9 - 1.1$ won't return the same result as $28.9 - 29.1$, as these are inherently not representable with the exact same inaccuracies

Because of this, the above equation is actually a non starter as it is not symmetric, and will introduce systematic asymmetric errors in your simulation. To fix this is quite the pain and, we'll now need a specific dirac delta discretisation in 3d to work with

## The actual dirac delta discretisation

The dirac delta function I'll be pilfering today is [this one (20)](https://arxiv.org/pdf/1611.07906). In general, you can construct 3d diracs quite straightforwardly, but this works well:

$$
\Delta_1(r, r_s) = \frac{1}{\pi r_s^3}
\begin{align}
\begin{cases}
1 - \frac{3}{2} (\frac{r}{r_s})^2 + \frac{3}{4} (\frac{r}{r_s})^3 \;\; &\mathrm{for}\;\; 0 \leq \frac{r}{r_s} \leq 1\\
\frac{1}{4}(2 - \frac{r}{r_s})^3 \;\; &\mathrm{for}\;\; 1 \leq \frac{r}{r_s} \leq 2\\
0 & \mathrm{otherwise}
\end{cases}
\end{align}
$$

$r$ is the radius of your point away from the particle

To fix our dirac problems, we need to rework this discretisation:

1. We need to re-express it in cell based coordinates, instead of world coordinates
2. It operating over the range $[0, 2]$ is very annoying

So we're instead going to take in a fraction from $[0, 1]$:

$$
\Delta_2(r_f, r_s) = \frac{1}{\pi (\frac{r_s}{2})^3}
\begin{align}
\begin{cases}
1 - \frac{3}{2} (2 r_f)^2 + \frac{3}{4} (2 r_f)^3 \;\; &\mathrm{for}\;\; 0 \leq 2 r_f \leq 1\\
\frac{1}{4}(2 - 2 r_f)^3 \;\; &\mathrm{for}\;\; 1 \leq 2 r_f \leq 2\\
0 & \mathrm{otherwise}
\end{cases}
\end{align}
$$

This means that $r_s$ is now the full size of the particle in world coordinates, and $r_f$ is an arbitrary fraction from 0 to 1. This now means that we can redefine the integral in 3d from earlier:

$$\sigma =  \int_{z_c - 0.5}^{z_c + 0.5} \int_{y_c - 0.5}^{y_c + 0.5} \int_{x_c - 0.5}^{x_c + 0.5} \Delta_2\left (\frac{\sqrt{(x - x_c^{\mathrm{idx}})^2 + (y - y_c^{\mathrm{idx}})^2 + (z - z_c^{\mathrm{idx}})^2}}{(\frac{r_s}{h})}, r_s \right ) dx dy dz$$

I use a trapezoidal method to perform the actual numerical integration. Of course, any error in the implementation of trapezoidal integration - including floating point contraction - will result in asymmetry creeping back in

## Symmetric trapezoidal, ish

Implementing a fully symmetric trapezoidal method would be very tricky. For numerical integration, it has the [following definition](https://en.wikipedia.org/wiki/Trapezoidal_rule):

$$\int^b_a f(x) dx = \Delta x \left (\frac{f(x_0) + f(x_N)}{2} + \sum^{n-1}_{k=1} f(x_k)\right )$$

Luckily for $N=2$ - which is good enough, this is actually straightforward. As long as we evaluate the right hand side sum, and the left hand side sum separately, then add them together at the end - it'll be symmetric. More iterations would require an outside in iteration scheme with pairwise matched summation

This is what I implemented (in 1d, just repeat the integral in 3d):

```c++
template<typename T, typename U>
inline
auto integrate_1d_trapezoidal(const T& func, int n, const U& upper, const U& lower)
{
    using variable_type = decltype(func(U()));

    variable_type sum = 0;

    for(int k=1; k < n; k++)
    {
        auto coordinate = lower + k * (upper - lower) / n;

        auto val = func(coordinate);

        sum += val;
    }

    return ((upper - lower) / n) * (0.5f * (func(lower) + func(upper)) + sum);
}
```

This only really just-so-happens to work for $N=2$, and its carefully written to avoid floating point contraction issues in the final expression - we'll still get a symmetric result if the compiler generates `fma(0.5f, func(lower) + func(upper), sum)`, and there are no other legal transforms that could cause us problems

This section has been one of the more complicated things I've had to implement. I do not know if I've ever seen a tediously correct implementation of the dirac delta function: most papers simply stop after the initial discretisation, which leads to an overall inaccuracy in the mass of a few % for very small dirac sizes. More importantly, the mass oscillates with a naive discretisation as a particle moves through the grid, and it introduces systematic errors

You can see that there are probably about ~10 points in total in this article where its possible to implement things incorrectly, which can rapidly lead to multiple rounding errors per-cell per-tick. This is the reason why its so important - if you do it wrong *everywhere*, then everything on one side of your grid will experience multiple non random bits of error relative to the other side of your grid every tick, which can lead to very unexpected results over time
