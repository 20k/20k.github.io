Hi there! Today we're going to examine how to do N-body particle physics, in general relativity. This is a bit of an underexplored topic compared to Newtonian N-body, and its easy to accidentally pick the wrong formalism or techniques for solving this problem. While the basic theory of what we're doing isn't complicated, there's a few major numerical problems to tackle today

At the end of this topic, we'll have about 10 million particles up and running at a decent speed - you'll also have received a crash course in IEEE floats, and the problems a spec oddity in C++ can cause

# What are we doing?

In both General Relativity, and Newtonian physics, we deal with pointlike particles when doing N-body dynamics. Each particle is fully described by its mass, position, and velocity in both formalisms

In Newtonian physics, each particle directly exerts a force on all other particles, which is famously:

$$F = \frac{G m_1 m_2}{r^2}$$

In general relativity, particles act through the (4d) stress energy tensor, and do not *directly* interact. For a single particle [(2.5)](https://scispace.com/pdf/3d-numerical-simulation-of-black-hole-formation-using-43u5c2u959.pdf0):

$$
T_{\mu\nu} = m \alpha^{-1} W^3 \delta^{(3)}(x^i - x_{\mathrm{p}}^i)\frac{u_\mu u_\nu}{u^0}\\
$$

|Symbol | Meaning |
|-|-|
|$m$ | The rest mass of a particle |
|$\alpha$ | Lapse, evaluated at $x^i$ |
| $W$ | Conformal factor, evaluated at $x^i$ |
| $\delta^{(3)}(x)$ | The 3d dirac delta function - this only takes a nonzero value when $x = 0$. This a non trivial term, and we'll have to discretise this |
| $x^i$ | The current coordinate position you're looking at |
| $x^i_{\mathrm{p}}$ | The position of the particle |
| $u_\mu$ | The 4-velocity of a particle, lowered |
| $u^0$ | The lorentz factor |

This is simply summed across all particles. Particles as you'd expect simply move via the geodesic equation, which is:

$$u^\mu \nabla_\mu u_\nu = 0$$

Clearly, we need to transplant this into the ADM formalism and spell out the equations more, but for once the general relativistic side of this is straightforward

# These equations in the ADM formalism

## Stress-energy

We need the ADM projections of the [stress energy tensor](https://en.wikipedia.org/wiki/Stress%E2%80%93energy_tensor#Isolated_particle) $T_{\mu\nu}$, to calculate the compatible terms for the BSSN equations. These are [(2.14, 2.15, 2.20)](https://scispace.com/pdf/3d-numerical-simulation-of-black-hole-formation-using-43u5c2u959.pdf):

$$
\begin{alignat}{2}
\rho_H &= \alpha W^3 &&\sum m u^0 \delta^{(3)}(x^i - x^i_{\mathrm{p}})\\
S_i &= W^3 &&\sum m u_i \delta^{(3)}(x^i - x^i_{\mathrm{p}})\\
S_{ij} &= \alpha^{-1} W^3 &&\sum m \frac{u_i u_j}{u^0} \delta^{(3)}(x^i - x^i_{\mathrm{p}})\\
\end{alignat}
$$

These quantities will be evaluated at every cell in our grid - except for $u^0$, which hides a significant amount of interpolation at $x^i_p$ in its calculation

## The geodesic equation

Given a 4-velocity $u^\mu = \frac{dx^\mu}{d\tau}$, the spatial components $u_i$ are evolved as follows [(2.9)](https://scispace.com/pdf/3d-numerical-simulation-of-black-hole-formation-using-43u5c2u959.pdf):

$$\begin{align}
\frac{d u_i}{dt} &= - \alpha u^0 \partial_i \alpha + u_j \partial_i \beta^j - \frac{u_j u_k}{2 u^0} \partial_i \gamma^{jk}\\
u^0 &= \frac{\sqrt{1 + \gamma^{ij} u_i u_j}}{\alpha}\\
\end{align}
$$

The particle's position is evolved as follows (via $\frac{dx^i}{dt} = \frac{u^i}{u^0}$):

$$
\frac{dx^i}{dt} = -\beta^i + \frac{\gamma^{ij} u_j}{u^0}
$$

Note that all the quantities evaluated here need to be interpolated from the grid at the particle's position $x^i_\mathrm{p}$ - keep this in mind for $u^0$. I precalculate $u^0$ in the evolution step, and re-use that in the stress-energy calculation

# The dirac delta function $\delta(x)$

The 1D dirac delta function $\delta^{(1)}(x)$ has the following definition:

$$\delta^{(1)}(x) =
\begin{align}
\begin{cases}
0, \; &x \neq 0 \\
\infty, \; &x = 0
\end{cases}
\end{align}
$$

$$\int^\infty_{-\infty} \delta^{(1)}(x) \; dx = 1$$

This says that the dirac delta function only takes a value at a single point $x=0$, and the area under this point is precisely $1$

![dirac1](/assets/nr6_dirac_1.png)

No real function actually meets this definition, so we must numerically approximate it somehow. Higher dimensional diracs are denoted by the raised index, and can be constructed via a product: eg $\delta^{(3)}(x, y, z) = \delta^{(1)}(x)\delta^{(1)}(y)\delta^{(1)}(z)$

## Numerical approximations

The solution is to essentially smear out the dirac delta function over a small area:

![dirac2](/assets/nr6_dirac_2.png)

There are an extremely wide variety of approximations we can use - we might demand that this new function has a few properties:

1. It is compactly supported, ie it has finite extent
2. It is smooth-ish
3. This function has an integral of 1

There isn't a super specific[^okso] reason to use one approximation over another today. The Dirac delta function I'll be pilfering is [this one (20)](https://arxiv.org/pdf/1611.07906), which is a function of radius

[^okso]: One property it would be nice if our dirac could maintain is that the generated effective self force (we'll get back to this) is exactly 0. I'm not sure if its possible to construct such a dirac though

$$
\Delta_1^{(3)}(r, r_s) = \frac{1}{\pi r_s^3}
\begin{align}
\begin{cases}
1 - \frac{3}{2} (\frac{r}{r_s})^2 + \frac{3}{4} (\frac{r}{r_s})^3 \;\; &\mathrm{for}\;\; 0 \leq \frac{r}{r_s} \leq 1\\
\frac{1}{4}(2 - \frac{r}{r_s})^3 \;\; &\mathrm{for}\;\; 1 \leq \frac{r}{r_s} \leq 2\\
0 & \mathrm{otherwise}
\end{cases}
\end{align}
$$

Where $r_s$ is the size in world coordinates of your particle, and this function takes values in the range $[0, 2 r_s]$. Many papers make the simple substitution $\delta^{(3)}(x, y, z) \rightarrow \Delta^{(3)}_1(r)$, and leave it at that

## Improving the numerical approximation

There's a bit of problem with making this simple substitution. To examine this, lets step back into 1D, and imagine a very basic dirac delta function $\Delta^{(1)}$:

$$\Delta^{(1)}(x) =
\begin{align}
\begin{cases}
1 - x, \; &\mid x\mid < 1 \\
0, \; \mathrm{otherwise}
\end{cases}
\end{align}
$$

When discretising, we create cells which are separated by a space of $h$. Our grid structure *samples* this function at eg $x-2h, x-h, x, x+h, x+2h$. If we evaluate the quantity:

$$\sum_1^n \Delta(x_n) \; h$$

We want that to be precisely $1$. In our discretisation as it stands currently however, there is absolutely no guarantee of it - this is only true in the limit as $h \rightarrow 0$. In fact, with small dirac delta function sizes, this may be significantly wrong!

![dirac3](/assets/nr6_dirac_3.png)

The remedy is to calculate the exact amount of the dirac delta function that intersects with a grid cell. We can do this by integrating:

$$\Delta^{(1)}_{\mathrm{good}} = \frac{\int_{x - \frac{h}{2}}^{x + \frac{h}{2}} \Delta^{(1)}(y) dy}{h}$$

in one dimension, or in three dimensions:

$$\Delta^{(3)}_{\mathrm{good}} = \frac{\int_{z - \frac{h}{2}}^{z + \frac{h}{2}} \int_{y - \frac{h}{2}}^{y + \frac{h}{2}} \int_{x - \frac{h}{2}}^{x + \frac{h}{2}} \Delta^{(3)}(\textbf{V}) d\textbf{V}}{h^3}$$

Where $x, y, z$ are the coordinates of a grid cell in world coordinates

![dirac4](/assets/nr6_dirac_4.png)

# IEEE and C++: A joyous combination

Let's examine the form of a general 1D integration in time problem, spatially discretised onto a grid:

|Cell Index|0|1|2|3|4|5|6|
|-|-|-|-|-|-|-|-|
|Value|$a_0$|$b_0$|$c_0$|$d_0$|$c_0$|$b_0$|$a_0$|

I've set up the initial conditions such that they're symmetric about the index $3$. After a single timestep into the future, we might expect our initial conditions to evolve to a new state:

|Cell Index|0|1|2|3|4|5|6|
|-|-|-|-|-|-|-|-|
|Value|$a_1$|$b_1$|$c_1$|$d_1$|$c_1$|$b_1$|$a_1$|

For any correct simulation, that symmetry should be preserved. In virtually all simulations however, you'll very immediately notice that this property does not hold up - and the two sides of the grid start to *increasingly* diverge. This is despite having the same initial conditions on both sides!

## Root causing the problems

This can be root caused to two similar problems:

1. Floating point arithmetic is not associative
2. C++ has special rules for transforming equations involving floats, via a little known loophole in the standard

Asymmetry can sneak in anywhere we look at adjacent grid cells or non central values (eg the dirac integral bounds). A first culprit to look at is differentiation. In general, 4th order numerical derivatives get implemented as follows:

```c++
float diff(const std::vector<float>& points, int idx, float scale)
{
    return (points[idx - 2] - 8 * points[idx - 1] + 8 * points[idx + 1] - points[idx + 2]) / (12 * scale);
}
```

This is evaluated from left to right. Lets check what we get for indices $2$, and $4$ - which should return exactly the same result:

$$\begin{align}
\mathrm{diff}_2 &= ((a_0 - (8 b_0)) + (8 d_1)) - c_1\\
\mathrm{diff}_4 &= ((c_0 - (8 d_0)) + (8 b_1)) - a_1\\
\end{align}$$

The issue is that after each floating point operation, a rounding step is performed implicitly. This means that these two expressions don't return the same results! This isn't a theoretical problem either, here's an example in [real-world code](https://github.com/GRTLCollaboration/GRChombo/blob/130140afe972701575740685343ea28f6ab8234c/Source/BoxUtils/FourthOrderDerivatives.hpp#L42)

This results in systematic differences in rounding on both sides of the grid, and this error can build up surprisingly fast as we've seen - as we're essentially preferentially discarding the low bits of our floats but biased in a specific direction. So ideally, we'd eliminate all the systematic sources of error in our simulation

You might think you can just rewrite this expression like this, by grouping equidistant cells:

```c++
float diff(const std::vector<float>& points, int idx, float scale)
{
    return ((points[idx - 2] - points[idx + 2]) + (-8 * points[idx - 1] + 8 * points[idx + 1])) / (12 * scale);
}
```

While correct in theory, surprisingly, tests will show that this still returns the wrong answer. What gives?

## The C++ standard loophole

In this piece of code:

```c++
float v1 = a*b + c;

float v_mul = a*b;
float v2 = v_mul + c;
```

C++ encourages that $v_1 \neq v_2$. This rather surprising feature is known as floating point contraction, and there is no standardised way to disable it[^pragma]. *Within an expression*, the compiler is free to turn anything of the form $a*b + c$ into $\mathrm{fma}(a, b, c)$, which may be both faster and more precise. Unfortunately - in our case, it also causes our 'fixed' code to be rewritten as follows:

[^pragma]: There is a non standard pragma inherited from C, but CUDA does not implement this which is a problem. Even then, the pragma is a very blunt force instrument, so you have to be pretty careful in general

```c++
float diff(const std::vector<float>& points, int idx, float scale)
{
    return ((points[idx - 2] - points[idx + 2]) + (fma(-8, points[idx - 1], 8 * points[idx + 1]))) / (12 * scale);
}
```

This reintroduces[^inpractice] the same issue we just tried to fix unfortunately. This can be fixed in a general way by spelling out all the intermediate variables, to create some really very beautiful code:

[^inpractice]: If you're wondering if this is a more theoretical problem, it isn't. GPU compilers are very aggressive about using this rule to emit FMAs where possible

```c++
float diff_long(const std::vector<float>& points, int idx, float scale)
{
    float vm2 = points[idx - 2];
    float vp2 = -points[idx + 2];
    float vm1 = -8 * points[idx - 1];
    float vp1 = 8 * points[idx + 1];

    float v2 = lm2 + lp2;
    float v1 = vm1 + vp1;
    float top = v1 + v2;

    return top / (12 * scale);
}
```

The above ('long form') represents the general form of how to fix this, and shows how to disable this compiler optimisation where necessary. For a specific problem, you may be able to rearrange it to negate this issue, eg:

```c++
float diff_concise(const std::vector<float>& points, int idx, float scale)
{
    return ((points[idx - 2] - points[idx + 2]) + 8 * (points[idx + 1] - points[idx - 1])) / (12 * scale);
}
```

This only works in our specific case for first derivatives - as the FMA that gets generated does not upset symmetry, and gives a 20% improvement in GPU-land over the long form version[^compiler]

Pairwise summation with explicitly spelt out intermediate variables is the general fix to this problem - and I apply the 'long form' technique anywhere which involves numerical derivatives (Kreiss-Oliger)

[^compiler]: This is at least partly due to compiler-itus, as compilers are much better at optimising within an expression, than across multiple expressions. Its a big part of the reason why I use code generation in these articles

## Fixing dirac

Another source of error is the way we've implement the dirac delta function. There are several sources of error here:

1. The integral bounds are arbitrary floats, which can lead to representation issues
2. The integration itself between $[-h/2, h/2]$ won't avoid this error out of the box

First off, lets swap everything to cell index based coordinates instead. I've also changed $\Delta$ to take in a fraction in the range $[0, 1]$, because its easier to reason about

$$
\Delta_2^{(3)}(r_f, r_s) = \frac{1}{\pi (\frac{r_s}{2})^3}
\begin{align}
\begin{cases}
1 - \frac{3}{2} (2 r_f)^2 + \frac{3}{4} (2 r_f)^3 \;\; &\mathrm{for}\;\; 0 \leq 2 r_f \leq 1\\
\frac{1}{4}(2 - 2 r_f)^3 \;\; &\mathrm{for}\;\; 1 \leq 2 r_f \leq 2\\
0 & \mathrm{otherwise}
\end{cases}
\end{align}
$$

This means that $r_s$ is now the full size of the particle in world coordinates, and $r_f$ is a fraction from 0 to 1. Now we can redefine the integral from earlier:

$$\Delta_{\mathrm{best}}^{(3)} =  \int_{z_c - 0.5}^{z_c + 0.5} \int_{y_c - 0.5}^{y_c + 0.5} \int_{x_c - 0.5}^{x_c + 0.5} \Delta_2\left (\frac{\sqrt{(x - x_c^{\mathrm{idx}})^2 + (y - y_c^{\mathrm{idx}})^2 + (z - z_c^{\mathrm{idx}})^2}}{(\frac{r_s}{h})}, r_s \right ) dx dy dz$$

Where $x_c, y_c, z_c$ represents the integral position of the cell in question in cell-based coordinates, and these half offsets can be represented exactly[^unsuref]. $x_c^{\mathrm{idx}}, y_c^{\mathrm{idx}}, z_c^{\mathrm{idx}}$ is the position of the particle, converted into those same cell based coordinates. This avoids the first set of numerical problems. Next up, we need to deal with the integration itself

[^unsuref]: If you're unsure of why, floating point guarantees the exact representability of whole numbers and fractional powers of $2$ when you have sufficient precision available

### Trapezoidal integration

Todo: Implement the fully symmetric trapezoidal method

Implementing a fully symmetric trapezoidal method would be a fair bit of work. For numerical integration, it has the [following definition](https://en.wikipedia.org/wiki/Trapezoidal_rule):

$$\int^b_a f(x) dx = \Delta x \left (\frac{f(x_0) + f(x_N)}{2} + \sum^{n-1}_{k=1} f(x_k)\right )$$

Luckily for $N=2$ - which is good enough - this is actually straightforward. As long as we evaluate the right hand side sum, and the left hand side sum separately, then add them together at the end - it'll be symmetric. More iterations would require an outside in iteration scheme with pairwise summation

This is what I implemented (in 1d, just repeat the integral in 3D):

```c++
template<typename T, typename U>
inline
auto integrate_1d_trapezoidal(const T& func, int n, const U& upper, const U& lower)
{
    using variable_type = decltype(func(U()));

    variable_type sum = 0;

    for(int k=1; k < n; k++)
    {
        auto coordinate = lower + k * (upper - lower) / n;

        auto val = func(coordinate);

        sum += val;
    }

    return ((upper - lower) / n) * (0.5f * (func(lower) + func(upper)) + sum);
}
```

Note that the returned value is carefully written to avoid problems

## Dirac: The end

This section has been one of the more complicated things I've had to implement. I do not know if I've ever seen a tediously correct implementation of the dirac delta function: most papers simply stop after the initial discretisation, which leads to an overall inaccuracy in the mass of a few % for small dirac sizes. More importantly, the mass oscillates with a naive discretisation as a particle moves through the grid, and it introduces systematic errors

There are about ~10 points in total in this article where its possible to implement things incorrectly, which can rapidly lead to multiple rounding errors per-cell per-tick. This is the reason why its so important - if you do it wrong *everywhere*, then everything on one side of your grid will experience multiple non random bits of error relative to the other side of your grid every tick, which can lead to very unexpected results over time

# Interpolation

As a reminder, our geodesic equation is as follows:

$$\begin{align}
\frac{d u_i}{dt} &= - \widehat{\alpha} u^0 \widehat{\partial_i \alpha} + u_j \widehat{\partial_i \beta^j} - \frac{u_j u_k}{2 u^0} \widehat{\partial_i \gamma^{jk}}\\
u^0 &= \frac{\sqrt{1 + \widehat{\gamma^{ij}} u_i u_j}}{\widehat{\alpha}}\\
\end{align}
$$

I've put hats over the variables that need to be interpolated at the particle's position $x^i_p$. A naive trilinear interpolation will lead to the same issues talked about above: Luckily, this is quite easily fixable:

```c++
template<typename T
inline
auto function_trilinear(T&& func, v3f pos)
{
    using namespace single_source;

    v3f floored = floor(pos);
    pin(floored);
    v3f frac = pos - floored;
    pin(frac);

    v3i ipos = (v3i)floored;

    auto c000 = func(ipos + (v3i){0,0,0});
    auto c100 = func(ipos + (v3i){1,0,0});

    auto c010 = func(ipos + (v3i){0,1,0});
    auto c110 = func(ipos + (v3i){1,1,0});

    auto c001 = func(ipos + (v3i){0,0,1});
    auto c101 = func(ipos + (v3i){1,0,1});

    auto c011 = func(ipos + (v3i){0,1,1});
    auto c111 = func(ipos + (v3i){1,1,1});

    auto lmix = [&](auto& a, auto& b, auto& t)
    {
        auto imx = no_opt(1-t);
        auto imimx = no_opt(1-imx);

        auto p1 = no_opt(imx * a);
        auto p2 = no_opt(imimx * b);

        return no_opt(p1 + p2);
    };

    auto c00 = lmix(c000, c100, frac.x());
    auto c01 = lmix(c010, c110, frac.x());

    auto c10 = lmix(c001, c101, frac.x());
    auto c11 = lmix(c011, c111, frac.x());

    auto c0 = lmix(c00, c01, frac.y());
    auto c1 = lmix(c10, c11, frac.y());

    return lmix(c0, c1, frac.z());
}
```

Note that `no_opt` in the scheme I'm using forces a variable declaration, to disable floating point contraction. `lmix` guarantees the property:

$$\mathrm{lmix}(a, b, t) == \mathrm{lmix}(b, a, 1-t)$$

Trilinear interpolation is otherwise a very standard algorithm, and not worth diving into. In many situations, trilinear interpolation is perfectly fine, but we'll have to go into when it is not

## Symmetric tricubic interpolation

The next step up from trilinear interpolation, is tricubic interpolation. It is common to use hermite[^hermite] interpolation - this kind of interpolation guarantees the values of the derivatives at the boundary, but this isn't a useful property for us

[^hermite]: Wikipedia will direct you to [this](https://citeseerx.ist.psu.edu/viewdoc/summary?doi=10.1.1.89.7835) paper, which is precisely the wrong approach. It's set up to be able to repeatedly perform Hermite interpolation with the same set of values, which is not what we want at all

What we want is tricubic Lagrangian interpolation, via a Lagrange interpolating polynomial. This does not require us to know the values of the derivatives anywhere, and it is both faster and more accurate than Hermite interpolation. It does have the downside that I now have to do more work though

### Cubic Lagrangian interpolation

The minimum number of points to do cubic interpolation is $4$. We'll operate in grid cells, which means that we have the following node structure:

| Node label | $x_0$ | $x_1$ | $x_2$ | $x_3$
|-|-|-|-|-|
|Value (ie the offset)|$-1$|$0$|$1$|$2$|

A cubic interpolating polynomial is constructed as follows (all bounds are inclusive):

$$\begin{align}
l_j = \prod_{m=0, m \neq j}^3 \frac{x - x_m}{x_j - x_m}\\
L(x) = \sum^3_{j} f_j l_j(x)\\
\end{align}
$$

$f_j$ represents the function value at the grid cell corresponding to the node. $x$ here is in the range $[0, 1]$, and represents the fractional offset of a particle's position with respect to the grid cells

A 3d polynomial can be constructed as follows:

$$L(x, y, z) = \sum^3_a \sum^3_b \sum^3_c f_{abc} l_a(x) l_b(y) l_c(z)$$

This is a large sum of 64 values. As you may be about to guess, you can't implement this as written otherwise you end up with systematic rounding errors. We instead have to perform a pairwise matched summation of all values, to ensure exactly the same order of operations on both sides of the grid

#### Simple but wrong

This is tricubic interpolation without any corrections for floating-point-and-C++-itus

```c++
template<typename T, typename... U>
inline
auto tricubic_particles(T&& func, v3f frac, v3i ifloored, U&&... args)
{
    using namespace single_source;

    std::array<float, 4> nodes = {
        -1,
        0,
        1,
        2
    };

    using value_v = decltype(func(v3i(), std::forward<U>(args)...));

    auto L_j = [&](int j, const valuef& f, float& bottom_out)
    {
        int bottom = 1;

        valuef out = 1;

        for(int m=0; m < 4; m++)
        {
            if(m == j)
                continue;

            bottom = bottom * (nodes[j] - nodes[m]);

            out = out * (f - nodes[m]);
        }

        bottom_out = (float)bottom;

        return out;
    };

    value_v sum = {};

    for(int z=0; z < 4; z++)
    {
        for(int y=0; y < 4; y++)
        {
            for(int x=0; x < 4; x++)
            {
                v3i offset = (v3i){x - 1, y - 1, z - 1};

                auto u = func(ifloored + offset, std::forward<U>(args)...);

                float bx = 0;
                float by = 0;
                float bz = 0;

                auto val = u * L_j(x, frac.x(), bx) * L_j(y, frac.y(), by) * L_j(z, frac.z(), bz);

                sum += val * (1/(bx * by * bz));
            }
        }
    }

    return sum;
}
```

#### Complex but correct

This is the pairwise matched summation version of the above. GPU loops are emitted instead of unrolled, as AMD appears to suffer when too many memory accesses are emitted

```c++
template<typename T, typename... U>
inline
auto tricubic_particles(T&& func, v3f frac, v3i ifloored, U&&... args)
{
    using namespace single_source;

    using value_v = decltype(func(v3i(), std::forward<U>(args)...));

    //I accumulate the top, and bottom portions of the lagrange interpolating polynomial basis functions separately
    //as the bottom is a collection of integral constants
    auto L_j = [&](valuei j, const valuef& f, mut<valuef>& bottom_out)
    {
        //evaluate a basis function
        auto apply_for_m = [&](int m)
        {
            mut<valuef> out = declare_mut_e(valuef(1));

            if_e(m != j, [&]{
                //node locations are implicitly calculated as label - 1
                as_ref(bottom_out) = declare_e(bottom_out) * ((valuef)j - 1.f - ((float)m - 1));

                as_ref(out) = (f - (valuef)(m - 1));
            });

            return declare_e(out);
        };

        return (apply_for_m(0) * apply_for_m(3)) * (apply_for_m(1) * apply_for_m(2));
    };

    auto sum = declare_mut_e(value_v());

    auto fetch_indices = [](valuei what)
    {
        return ternary(what == 0, (v2i){0,3}, (v2i){1, 2});
    };

    mut<valuei> iz = declare_mut_e(valuei());

    for_e(iz < 2, assign_b(iz, iz+1), [&]{
        mut<valuei> iy = declare_mut_e(valuei());

        for_e(iy < 2, assign_b(iy, iy+1), [&]{
            mut<valuei> ix = declare_mut_e(valuei());

            for_e(ix < 2, assign_b(ix, ix+1), [&]{
                auto xs = fetch_indices(declare_e(ix));
                auto ys = fetch_indices(declare_e(iy));
                auto zs = fetch_indices(declare_e(iz));

                //evaluates the interior term of the sum
                auto eval_for = [&](valuei x, valuei y, valuei z)
                {
                    v3i offset = (v3i){x - 1, y - 1, z - 1};

                    auto u = func(ifloored + offset, std::forward<U>(args)...);

                    mut<valuef> bx = declare_mut_e(valuef(1));
                    mut<valuef> by = declare_mut_e(valuef(1));
                    mut<valuef> bz = declare_mut_e(valuef(1));

                    auto val = no_opt(u * L_j(x, frac.x(), bx) * L_j(y, frac.y(), by) * L_j(z, frac.z(), bz));

                    return no_opt(val * (1/(declare_e(bx) * declare_e(by) * declare_e(bz))));
                };

                auto v000 = eval_for(xs[0], ys[0], zs[0]);
                auto v100 = eval_for(xs[1], ys[0], zs[0]);

                auto v010 = eval_for(xs[0], ys[1], zs[0]);
                auto v110 = eval_for(xs[1], ys[1], zs[0]);

                auto v001 = eval_for(xs[0], ys[0], zs[1]);
                auto v101 = eval_for(xs[1], ys[0], zs[1]);

                auto v011 = eval_for(xs[0], ys[1], zs[1]);
                auto v111 = eval_for(xs[1], ys[1], zs[1]);

                auto v00 = v000 + v100;
                auto v10 = v010 + v110;
                auto v01 = v001 + v101;
                auto v11 = v011 + v111;

                auto v0 = v00 + v10;
                auto v1 = v01 + v11;

                as_ref(sum) += (v0 + v1);
            });
        });
    });

    return declare_e(sum);
}
```

The naive implementation of this is simple, but my goodness is this a joy. Even without the systematic numerical issues, pairwise summation has a reduced error term - so its better than just a big linear sum

# Initial conditions

There are three components to the initial conditions:

1. Define the particle's 4-velocity
2. Solve the hamiltonian constraint
3. Possibly solve the momentum constraint

## 4-velocity

Here, velocity is defined relative to the inertial frame of reference of the particle. This means that to calculate the 4-velocity, we need to first construct a tetrad. While in the general case you'll need to [Gram-Schidt](https://en.wikipedia.org/wiki/Gram%E2%80%93Schmidt_process) the metric to find a set of tetrads (eg see [here](https://20k.github.io/c++/2024/06/19/tetrads.html)), our initial conditions will always produce a diagonal metric - which makes tetrad construction straightforward

Firstly, take the following initial slice: $\alpha = 1, \beta^i = 0$. Then, we can construct the metric tensor as follows:

$g_{\mu\nu} =$

||0|1|2|3|
|-|-|-|-|-|
|0|-1| | | |
|1|  |$\gamma_{00}$| | |
|2|  |  |  $\gamma_{11}$| |
|3|  |  |  | $\gamma_{22}$ |

This gives the tetrads via the usual relation for diagonal metrics (ie [1.4.21](https://arxiv.org/pdf/0904.4184)):

$$\begin{align}
e_0^0 &= 1\\
e_1^1 &= \frac{1}{\sqrt{\gamma_{00}}}\\
e_2^2 &= \frac{1}{\sqrt{\gamma_{11}}}\\
e_3^3 &= \frac{1}{\sqrt{\gamma_{22}}}\\
\end{align}$$

The lower index labels the tetrad vector, and the upper index labels the coordinate. From here, you first construct a 4-velocity locally, and then use the tetrad to find the global 4-velocity:

$$\begin{align}
\gamma &= \frac{1}{\sqrt{1 - \mid v \mid^2}}\\
v_{flat}^{\mu} &= \gamma(1, v_0, v_1, v_2)\\
v_{curved}^\mu &= e_i^\mu v_{flat}^i
\end{align}$$

Note that the $i$ index runs from $0$ to $4$ contrary to the rest of this article, as this is standard notation for tetrads[^notthesame]. $v_{curved}$ is the final velocity of the particle

[^notthesame]: This use of index notation isn't really the same as other uses, as the lower index of a tetrad is only denoting the label of which vector you're talking about (rather than it having co and contravariant indices). Tetrad indices when inverted correspond to a matrix inversion (when treating the tetrad vectors as the column vectors of a 4x4 matrix), and does not involve the metric tensor

## Hamiltonian constraint solving

Its important to solve the hamiltonian constraint as part of the initial conditions, because errors here are quite sticky, and can leave visual 'welts' on your simulation that are very noticeable. The hamiltonian constraint that we'll be using can be derived from [2.11](https://arxiv.org/pdf/1905.08890), and with the standard set of constraints looks like this:

$$
\nabla \psi = - \psi^{-7} \bar{A}_{ij} \bar{A}^{ij} - 2 \pi \psi^5 \rho_H
$$

$\rho_H$ is the source term for the stress-energy tensor, and I'm keeping the same notation from the matter article. To keep solving, we need two things:

1. $\rho_H$ (the scalar source term for the stress-energy tensor)
2. $\bar{A}_{ij}$ (the extrinsic curvature)

### $\rho_H$

We already know that:

$$\rho_H = \alpha W^3 \sum m u^0 \delta^{(3)}(x^i - x^i_{\mathrm{p}})$$

The only issue is that we don't have a value of $W$ that we can use (we'll implicitly set $\alpha = 1$). To solve this, we know that:

$$\begin{align}
\bar{\gamma}_{ij} \psi^4 &= \gamma_{ij}\\
\tilde{\gamma}_{ij} &= W^2 \gamma_{ij}\\
\end{align}
$$

Apply the rules of determinants:

$$\begin{align}
det(\bar{\gamma}_{ij} \psi^4) &= det(\gamma_{ij}) = det(\tilde{\gamma}_{ij} W^{-2})\\
(\psi^4)^3 &= (W^{-2})^3\\
\psi^{12} &= W^{-6}\\
\psi^{-6} &= W^3\\
\end{align}
$$

Lets now define $\bar{\rho}_H = \sum m u^0 \delta^{(3)}(x^i - x^i_{\mathrm{p}})$, ie dropping the conformal factor (and setting $\alpha=1$). This means you may rewrite the hamiltonian constraint as this:

$$\nabla \psi = - \psi^{-7} \bar{A} _{ij} \bar{A}^{ij} - 2 \pi \psi^{-1} \bar{\rho}_H$$

This is actually solvable, aside from $\bar{A}_{ij}$. To figure that out, we'll dip into the momentum constraint

## $\bar{A}_{ij}$ and the momentum constraint

When our particles are not moving, $\bar{A}_{ij} = 0$ - and bob's your uncle. All particle papers I have looked at use stationary particles, and it seems like nobody wants to touch this problem with a 100ft barge pole. As a professional barge pole toucher, this question has been haunting me for a while

One approach is to repurpose the [neutron star](https://arxiv.org/pdf/1606.04881) initial conditions paper - set the pressure to $0$, and to model a body without spin. When an object does not have spin, the solution becomes spherically symmetric. The reduced problem is as follows:

$$\begin{align}
\bar{A}^{ij} &= \frac{3Q}{2r^2}(P^i l^j + P^j l^i - (\eta^{ij} - l^i l^j) P_i l^i)\\
Q &= \int^r_0 4 \pi \sigma(x) x^2 dx\\
\sigma(x) &= \frac{\tilde{\rho}_H}{\mathcal{M}}\\
\mathcal{M} &= 4 \pi \int^{r_0}_0 \tilde{\rho}_H r^2 dr\\
\end{align}$$

Strictly speaking, this is approximate - as it assumes that $W$ is constant within the body, and so disappears in the normalisation factor $\mathcal{M}$. Tests show that this reduces the momentum constraint violations significantly. This isn't worth solving for the following reasons:

1. Generally we're dealing with relatively low velocity particles, so $\bar{A}_{ij} \approx 0$ anyway
2. All formalisms are momentum constraint damped, so errors disappear quickly
3. It involves summing across all particles over all points of the grid, which is very bad perf-wise. In general you'll likely want to merge nearby particles, and perform other grouping approximations which are non trivial

I've bundled an implementation of this in with the article, but its switched off by default. Because it has minimal value, I'm not going to dig into this more

Implicit midpoint has the form:

$$
y_{n+1} = y_n + h f(\frac{1}{2}(y_n + y_{n+1}))

When evaluated via fixed point iteration, the first iteration has $y_n == y_{n+1}$. It is a significant performance improvement to manually spell this out in the code to cut the cost of that first iteration

#### The actual equations

```c++
auto icY = cY.invert();
auto iYij = icY * (W*W);

valuef au0_sq = 1 + iYij.dot(vel, vel);
valuef u0 = sqrt(au0_sq) / gA;
pin(u0);

v3f dX = -gB + iYij.raise(vel) / u0;

v3f dV;

{
    v3f p1 = -gA * u0 * dgA;

    v3f p2;

    for(int i=0; i < 3; i++)
    {
        valuef sum = 0;

        for(int j=0; j < 3; j++)
        {
            sum += vel[j] * dgB[i, j];
        }

        p2[i] = sum;
    }

    v3f p3;

    //Y^jk,i = u dvdx + v dudx
    //(W^2 cY^jk),i = W^2 (cY^jk,i) + cY^jk (W^2),i
    //= W^2 (cY^jk,i) + cY^jk 2 W dW[i]

    for(int i=0; i < 3; i++)
    {
        metric<dual<valuef>, 3, 3> d_cYij;

        for(int j=0; j < 3; j++)
        {
            for(int k=0; k < 3; k++)
            {
                d_cYij[j, k].real = cY[j, k];
                d_cYij[j, k].dual = dcY[i, j, k];
            }
        }

        pin(d_cYij);

        auto dicY = d_cYij.invert();
        pin(dicY);

        valuef sum = 0;

        for(int j=0; j < 3; j++)
        {
            for(int k=0; k < 3; k++)
            {
                valuef licy = pow(W, 2) * dicY[j, k].dual + cY[j, k] * 2 * W * dW[i];

                sum += -(vel[j] * vel[k] / (2 * u0)) * licy;
            }
        }

        p3[i] = sum;
    }

    dV = p1 + p2 + p3;
}

pin(pos_base);
pin(vel_base);
pin(dX);
pin(dV);
pin(u0);

for(int i=0; i < 3; i++)
    as_ref(p_out.positions[i][id]) = pos_base[i] + timestep.get() * dX[i];

for(int i=0; i < 3; i++)
    as_ref(p_out.velocities[i][id]) = vel_base[i] + timestep.get() * dV[i];

as_ref(lorentz_out[id]) = u0;
```

The only complex part is evaluating $\partial_i \gamma^{jk}$. I Leibnitz this to get it into the following form:

$$
W^2 \partial_i \tilde{\gamma}^{jk} + 2 W \partial_i W \tilde{\gamma}^{jk}
$$

And then use dual numbers to evaluate $$\partial_i \tilde{\gamma}^{jk}$$ from $$\partial_i \tilde{\gamma}_{jk}$$

### The mass boundary condition

There are two case in which we need to delete particles:

1. As they approach the boundary of the simulation
2. In the event horizon of a black hole, to avoid the simulation blowing up

Firstly, particles with no mass are simply not evolved (nor do they contribute to the stress-energy tensor)

```c++
if_e(!isfinite(mass) || mass == 0, [&]{
    for(int i=0; i < 3; i++)
        as_ref(p_out.positions[i][id]) = pos_base[i];

    for(int i=0; i < 3; i++)
        as_ref(p_out.velocities[i][id]) = vel_base[i];

    as_ref(lorentz_out[id]) = valuef(1.f);
    as_ref(p_out.masses[id]) = mass;

    return_e();
});
```

Instead of a fully hard delete (which can lead to a sudden burst of constraint violations), I use the following approach:

1. A soft damping in the interior of the black hole, or as the particle approaches the boundary
2. A strict cutoff when the mass is below a cutoff value, or is close to the boundary

```c++
valuei dist = distance_to_boundary((v3i)round(grid_next), dim.get());

if_e(dist <= 10 || gA < 0.15f, [&]{
    as_ref(p_out.masses[id]) = max(p_base.masses[id] + timestep.get() * -p_in.masses[id], 0.f);
});

if_e(dist <= 5 || p_in.masses[id] <= mass_cutoff.get(), [&]{
    as_ref(p_out.masses[id]) = valuef(0.f);
});
```

The mass cutoff is determined as 10% of the mass of the lightest particle's initial mass, which is a number derived entirely by vibes

## Calculating the stress-energy tensor

Each particle has a size, and generate a contribution to the stress-energy tensor. We need to - somehow - sum all the contributions from every particle onto the grid. I think I've finally come up with a decent approach here, which is free of the limitations of older methods I've explored in the past

The basic idea is as follows:

1. Loop over the size (in cells) of the particle, determined by the dirac delta size
2. Accumulate the stress energy tensor on the grid directly, using 64-bit fixed point

This is not my first rodeo at solving this problem, but I think its the best approach so far. While using 64-bit atomics may seem suboptimal, other techniques have downsides which are discussed at the end of the article

### Looping over the size in cells of the particle

I define the size of a particle in cells instead of in world coordinate, as this the easiest to work with. This gets plugged into the dirac delta function (which remember: we modified the definition of to take a unit fraction)

This gives a simple loop procedure:

```c++
void for_each_dirac(v3i dim, valuef scale, v3f dirac_pos, int radius_cells, auto&& func)
{
    using namespace single_source;
    assert(radius_cells > 0);

    v3f fpos = world_to_grid(dirac_pos, dim, scale);

    v3i cell = (v3i)floor(fpos);
    pin(cell);

    //The appropriate modification is rightwards + 1, leftwards + 0
    int spread = radius_cells + 1;

    mut<valuei> z = declare_mut_e(valuei(-radius_cells));

    for_e(z <= spread, assign_b(z, z+1), [&]{
        mut<valuei> y = declare_mut_e(valuei(-radius_cells));

        for_e(y <= spread, assign_b(y, y+1), [&]{
            mut<valuei> x = declare_mut_e(valuei(-radius_cells));

            for_e(x <= spread, assign_b(x, x+1), [&]{
                v3i offset = {declare_e(x), declare_e(y), declare_e(z)};
                offset += cell;
                pin(offset);

                valuef dirac = integrate_dirac_gpu(dirac_delta<valuef>, (v3f)offset, fpos, radius_cells, scale);
                pin(dirac);

                if_e(dirac > 0, [&]{
                    func(offset, dirac);
                });
            });
        });
    });
}
```

The interesting parts here are:

1. `dirac_pos` is just the particle position
2. The cells that the dirac delta function covers must be offset by one in the *rightwards* direction, as its origin can take fractional positions
3. These loops are not unrolled on the GPU, as it causes very bad performance issues
4. Many of the cells are simply skipped. It would be a lot more efficient to directly iterate over a sphere, than a cube

### Accumulation

This is one of the most critical kernels in the entire program, so I'm going to parse out the interesting bits here:

```c++
void calculate_particle_intermediates(execution_context& ectx,
                                      particle_base_args<buffer<valuef>> particles_in,
                                      buffer<valuef> lorentz_in,
                                      particle_utility_args<buffer_mut<valuei64>> out,
                                      literal<v3i> dim, literal<valuef> scale, literal<value<size_t>> particle_count,
                                      literal<valued> fixed_scale, int radius_cells)
{
    using namespace single_source;

    value<size_t> id = value_impl::get_global_id_us(0);
    pin(id);

    if_e(id >= particle_count.get(), [&]{
        return_e();
    });

    valuef lorentz = lorentz_in[id];
    valuef mass = particles_in.get_mass(id);
    v3f pos = particles_in.get_position(id);
    v3f vel = particles_in.get_velocity(id);

    pin(pos);
    pin(vel);
    pin(mass);
    pin(lorentz);

    if_e(!isfinite(mass) || mass == 0, [&]{
        return_e();
    });

    for_each_dirac(dim.get(), scale.get(), pos, radius_cells, [&](v3i offset, valuef dirac) {
        valuef E = mass * lorentz * dirac;
        v3f Ji = mass * vel * dirac;

        tensor<valuef, 3, 3> Sij;

        for(int i=0; i < 3; i++)
        {
            for(int j=0; j < 3; j++)
            {
                Sij[i, j] = (mass * vel[i] * vel[j] / lorentz) * dirac;
            }
        }

        std::array<valuef, 6> Sij_sym = extract_symmetry(Sij);

        auto scale = [&](valuef in)
        {
            valued in_d = (valued)in;
            valued in_scaled = in_d * fixed_scale.get();

            return (valuei64)round((valuef)in_scaled);
        };

        valuei64 E_scaled = scale(E);

        std::array<valuei64, 3> Si_scaled;

        for(int i=0; i < 3; i++)
            Si_scaled[i] = scale(Ji[i]);

        std::array<valuei64, 6> Sij_scaled;

        for(int i=0; i < 6; i++)
            Sij_scaled[i] = scale(Sij_sym[i]);

        valuei idx = offset.z() * dim.get().y() * dim.get().x() + offset.y() * dim.get().x() + offset.x();

        valuei64 val = out.E.atom_add_e(idx, E_scaled);

        //basic overflow detection, as E > 0
        if_e(val < 0, [&]{
            print("Error in particle dynamics\n");
        });

        for(int i=0; i < 3; i++)
            out.Si_raised[i].atom_add_e(idx, Si_scaled[i]);

        for(int i=0; i < 6; i++)
            out.Sij_raised[i].atom_add_e(idx, Sij_scaled[i]);
    });
}
```

#### Fixed point conversion

You might notice that the fixed point scaling is handled as follows:

```c++
auto scale = [&](valuef in)
{
    valued in_d = (valued)in;
    valued in_scaled = in_d * fixed_scale.get();

    return (valuei64)round((valuef)in_scaled);
};
```

There's an extra intermediate rounding to `float` (`valuef`) which may seem strange. Its unfortunately a significant performance win to do this (I don't know why - possibly because AMD's handling of the maths library can be odd), which means that we have to check if this step is well motivated

Either way, the calculation of the scale factor for fixed point is critical for accuracy

#### Fixed point scale factor

There are two primary concerns with calculating the fixed point scale factor:

1. We'd like as much accuracy as possible
2. The simulation must be able to tolerate a significant overlap of particle contributions without overflowing

The largest, most significant term is $E$, which has the form `mass * lorentz * dirac`. Given that `dirac` maxes out at $1$, and `lorentz` $\approx 1$, I assume that the maximum contribution of a particle to a cell is roughtly `mass`

That means that for a single particle, if you set the fixed point to be $F = \frac{K}{mass}$, the resulting integral value will have a value of approximately $K$. So in total, this means that you can easily define:

```c++
double get_fixed_scale(double total_mass, int64_t particle_count)
{
    return ((double)particle_count / total_mass) * pow(10., 7.);
}
```

This means that each particle gets $10^7 \approx 2^{12}$ bits of precision per cell, and each cell can hold $\approx 2^{64-12}$ dirac samples. This also gives a lot of headroom, while providing adequate precision. Note that the number of dirac samples far exceeds the number of particles, as each particle overlaps multiple cells

I list a transparent performance improvement to this scheme at the end of this article

#### Fixed point -> Float

To actually consume the data in the BSSN kernel, I convert the 64-bit fixed point back into floats as a separate pass via a simple division. This uses a bit more memory, and could probably be eliminated or done in place

## An optional performance improvement

Particles have their properties stored in a big linear buffer. This means that, assuming particles are distributed randomly, memory is accessed randomly when accumulating particle data and performing the evolution kernels

One fix for this is to perform a partial sorting, to group particles in the same cell together in memory. I do this via a simple slab allocator, which has excellent performance characteristics

```c++

void count_particles_per_cell(execution_context& ectx, std::array<buffer<valuef>, 3> pos, buffer_mut<valuei> cell_counts, literal<v3i> dim, literal<valuef> scale, literal<value<size_t>> particle_count)
{
    using namespace single_source;

    value<size_t> id = value_impl::get_global_id_us(0);
    pin(id);

    if_e(id >= particle_count.get(), [&]{
        return_e();
    });

    v3f world_pos = {pos[0][id], pos[1][id], pos[2][id]};
    pin(world_pos);

    v3f grid_posf = world_to_grid(world_pos, dim.get(), scale.get());
    pin(grid_posf);
    v3i grid_pos = (v3i)floor(grid_posf);

    grid_pos = clamp(grid_pos, (v3i){0,0,0}, dim.get() - 1);

    valuei idx = grid_pos.z() * dim.get().x() * dim.get().y() + grid_pos.y() * dim.get().x() + grid_pos.x();

    cell_counts.atom_add_e(idx, 1);
}

void memory_allocate(execution_context& ectx, buffer_mut<valuei> counts, buffer_mut<valuei> memory_ptrs, buffer_mut<valuei> memory_allocator, literal<valuei> work_size)
{
    using namespace single_source;

    valuei id = value_impl::get_global_id(0);
    pin(id);

    if_e(id >= work_size.get(), [&]{
        return_e();
    });

    valuei my_count = counts[id];

    mut<valuei> my_memory = declare_mut_e(valuei(0));

    if_e(my_count > 0, [&]{
        as_ref(my_memory) = memory_allocator.atom_add_e(valuei(0), my_count);
    });

    as_ref(memory_ptrs[id]) = declare_e(my_memory);
    as_ref(counts[id]) = valuei(0);
}

void permute_memory(execution_context& ectx, particle_base_args<buffer<valuef>> in, particle_base_args<buffer_mut<valuef>> out, buffer_mut<valuei> memory_ptrs, buffer_mut<valuei> cell_counts, literal<v3i> dim, literal<valuef> scale, literal<value<size_t>> particle_count)
{
    using namespace single_source;

    value<size_t> id = value_impl::get_global_id_us(0);
    pin(id);

    if_e(id >= particle_count.get(), [&]{
        return_e();
    });

    v3f world_pos = in.get_position(id);
    pin(world_pos);

    v3f grid_posf = world_to_grid(world_pos, dim.get(), scale.get());
    pin(grid_posf);
    v3i grid_pos = (v3i)floor(grid_posf);

    grid_pos = clamp(grid_pos, (v3i){0,0,0}, dim.get() - 1);

    valuei idx = grid_pos.z() * dim.get().x() * dim.get().y() + grid_pos.y() * dim.get().x() + grid_pos.x();

    valuei my_offset = cell_counts.atom_add_e(idx, 1);
    valuei cell_offset = memory_ptrs[idx];
    pin(cell_offset);

    valuei idx_out = my_offset + cell_offset;

    for(int i=0; i < 3; i++)
    {
        as_ref(out.positions[i][idx_out]) = in.positions[i][id];
        as_ref(out.velocities[i][idx_out]) = in.velocities[i][id];
    }

    as_ref(out.masses[idx_out]) = in.masses[id];
}
```

These three kernels are run sequentially, and this provides a significant speedup
